# ナットク台帳

> チラシや LINE を見た人が、本当に店に来たのか。来店までを1本の台帳でつなぎ、Claude が台帳を掘って「次の一手」まで出す、地域の店のための台帳です。

ハッカソンの後は、作者（全社の DX 担当）が担当する店のチラシ・LINE の施策で試し、マネージャー会議の資料に「来店・クーポンの数と次の一手」を足します。

## なぜ作ったか

全社の DX 担当として、店のチラシや LINE の効果を、UTM を付けて GA4・Clarity で計り、Looker Studio にまとめてマネージャー会議に出してきました。けれど計れるのは Web の上の「見られた・押された」まで。予約と来店は店の側の記録で、チラシを見た人が本当に来店したかは分かりません。LP にはクーポンのボタンもありますが、店で使われたかも分かりません。3ページに並んだ数字から「なぜか・次に何をするか」を読み解くのも、見る人まかせになっています。

ナットク台帳は、チラシや LINE から来店までを1本の台帳でつなぎます。Claude（Managed Agents の分析エージェント）が台帳を自分で数え直して見立てを確かめ、次の一手と見る数字まで出します。次の分析は、その一手のその後を振り返ります。DX 担当がいなくても、店長が自分で回せる形を目指しています。

（店・お客様・数字はすべて見本です。実在の店のデータは入っていません。）

### 手元で起動する

必要なもの：[uv](https://docs.astral.sh/uv/)（Python は uv が用意します）。Windows・Mac・Linux で同じ手順です。

```sh
git clone https://github.com/yoshi-tune/visit-ledger.git
cd visit-ledger
uv run uvicorn app.main:app              # http://127.0.0.1:8000/ を開く
```

初めての起動で、見本の台帳 `data/ledger.db` を自動で作ります（乱数の種を固定しているので、誰が作っても同じ中身）。台帳を作り直す時は `uv run python scripts/make_sample.py` を回してください。

**鍵が無くても最後まで試せます。** 効果の画面で「分析を頼む」を押すと、見本の台帳で Claude（Opus 5.5）が実際に分析した時の報告を「見本の報告」として出します（Claude は呼びません。続けての質問はできません）。デモ動画の分析は、鍵を入れた本物の分析です。

本物の分析も試す場合（任意。1回 $1 前後かかります）：

```powershell
# Windows（PowerShell）
$env:ANTHROPIC_API_KEY = "<あなたの鍵>"
uv run python scripts/setup_agent.py     # 分析エージェントを1回だけ作る（ID は data/agent_ids.json に入る）
uv run uvicorn app.main:app
```

```sh
# Mac・Linux
export ANTHROPIC_API_KEY="<あなたの鍵>"
uv run python scripts/setup_agent.py
uv run uvicorn app.main:app
```

効果の画面と分析の画面に出る費用は、定価で数えた目安です（正しい額は Claude Console で確かめてください）。`make_sample.py` で台帳を作り直すと、分析の記録と費用の合計も消えます。1回の上限は環境変数 `VL_BUDGET_CENTS`（セント・既定 300）で変えられます。

## 使い方

アプリの「今日」は **2026-11-07** に固定しています（見本データと時計をそろえるため）。

1. **LP**（スマホ向け）：<http://127.0.0.1:8000/lp/S-EKI?campaign=autumn_check_202610&src=flyer> を開き、「空いている日時を見る」
2. **予約**：メニュー → 日にち（今日 11/7 を選ぶ）→ 空いている時間 → 名前・電話（見本の値で可）→ 確認。送った時点で予約が確定し、予約番号が出る
3. **受付**：<http://127.0.0.1:8000/desk> の「今日の予約」で「来店」
4. **効果の画面**：<http://127.0.0.1:8000/dashboard> でチラシの数字が変わったことを見る →「分析を頼む」
5. **店の設定**：<http://127.0.0.1:8000/settings> で時間帯ごとの台数・休みの曜日・休みの日を変えると、予約の画面にすぐ反映される（見本の初期値：10〜16時の6枠に各2台・毎週水曜は休み）
6. **クーポン**：LP の「クーポン（点検 ¥500 引き）」で QR と番号が出る。受付の <http://127.0.0.1:8000/desk/coupon> に番号を入れる（店のスマホで QR を読むと同じ画面が開く）。予約のある人は「来店とクーポンを記録する」の1回で来店とクーポンが台帳に残り、予約の無い人は「予約なしの来店」として残る。効果の画面のクーポンの欄が変わる。間違えて押した「使った」は、同じ画面で取り消せる（取り消した記録も台帳に残る）
7. **分析担当の見直し**：<http://127.0.0.1:8000/improve> で、分析担当（AI）が自分の仕事のやり方を直した案と、届く報告の前と後・確かめた結果を見る。本番に使うかは人が押して決める（仕組みは [docs/IMPROVE.md](docs/IMPROVE.md)）

## この台帳で分かること・分からないこと

- **追えるのは、施策の URL（チラシの QR・LINE のリンク）から LP を開いた所から。** 配った紙を誰が受け取ったかは追いません。配った数は参考の値です
- **予約・クーポンを結ぶのは、同じ LP の閲覧の記録（同じスマホ・同じブラウザー）。** 同じ人かどうかは確かめていません。電話で予約した人や、別のスマホでクーポンを見せた人は「予約なしの来店」に見えます
- **予約の枠は、ネット予約の枠です。** 電話の予約や今の予約帳とは自動ではそろわないので、分けて使う前提です（例：ネット予約は各時間1台まで）。整備の中身ごとの作業時間は見ていません
- **割引で得をしたか・利益・施策をやらなかった時と比べて増えた分は、測っていません。** 分かるのは、施策ごとの「LP → 予約 → 来店 → クーポン」の数と、その読み解きです
- **前回の一手の振り返り**は、一手を実際にやったかの記録が台帳に無いので、数字の変化を一手の効果とは言いません
- **分析担当の見直しで「良くなった」**のは、答えの分かっている2つの見本の台帳と、決めた物差しでの話です。ほかの台帳や本物の店で良くなったことまでは確かめていません
- **受付・クーポンの受付・店の設定・見直しの画面に、合言葉はまだありません。** 手元で試すための形です（公開する時に付けます）

## Claude の使い方

アプリが数えるのは「何件か」まで。**「なぜか・次に何をするか」を読み解くのが、作品の中の Claude の仕事**です。その読み解きを、見本の台帳で確かめながら Claude 自身が直していきます。

### 作品の中の Claude

| 役 | モデル・機能 | なぜそれにしたか |
|---|---|---|
| **分析担当**（効果の画面の「分析を頼む」） | **Managed Agents**（既定 Opus 5.5。Sonnet 5.5・Haiku 5.5 も選べる）。サンドボックスでコードを書いて実行する | 数字を文章で推し量らせず、台帳の書き出し（CSV）を自分で数え直させるため。集計1回ごとに `step_NN.py` を書いて実行し、その数字だけを報告に使う |
| 　└ 外に出さない | Web の検索・取得を切り、通信を制限した環境。渡すのは個人情報の列を落とした CSV（番号は仮の番号に置き換え）と、アプリの集計だけ | 店のお客様の情報を Claude に渡さない・外にも出さないため（列を落とすのは書き出しの関数1か所） |
| 　└ 合格までやり直す | outcomes（`define_outcome`）に採点の基準 `agent/rubric.md` を渡し、最大3回までやり直す | 検算の一致・件数が少ない時の断り・「効果と言い切らない」などを、エージェントが自分で満たすまで直させるため |
| 　└ 使い過ぎない | 1回の上限額（既定 $3.00、`VL_BUDGET_CENTS`）を超えたら止める | 思わぬ費用を防ぐため。分析ごとの費用の目安は、分析の画面と効果の画面に出す |
| 　└ 続けて質問 | 終えた分析と同じセッションに質問を送る（`chat_NN.py` で数え直して答える） | 前の集計と CSV が残った作業場所で、そのまま掘り下げられるため |
| 　└ 前回を振り返る | 前回の「次の一手」と、その時の集計を `previous.json` で渡す | 次の分析が、前回の一手のその後を数え直すため（記録の直しと新しい予約・来店を分け、一手の効果とは言い切らない） |
| 予備の形 | Messages API を1回（`VL_ANALYSIS_MODE=messages`）。同じ報告の形（JSON Schema）で返す | Managed Agents が使えない時でも、同じ画面に報告を出すため |
| **分析担当の手順書を直す役**（[docs/IMPROVE.md](docs/IMPROVE.md)） | Opus 5.5（`effort: high`・JSON Schema の出力） | 採点で直しを求められた理由と前の回の結果を読み、手順書の1〜3か所を直す。直してはいけない節（数え方・言わないこと・報告の形）に触れた案は、コードで捨てる |
| **中身を確かめる役** | Sonnet 5.5 と、決まった問い `agent/judge.md`（直す役からは変えられない） | 仕掛けありの台帳で本当の理由（予約から来店予定日までの日数）を見つけたか、仕掛けなしの台帳で偶然かもしれない差を言い切らなかったかを、毎回同じ問いで確かめるため |
| **言い直し役** | Sonnet 5.5（断られた時は Opus 5.5 で聞き直す） | 直しの説明を、店長の言葉と「届く報告の前と後」にするため。抜き出した文が本当に報告にあるかはコードで確かめ、無ければ捨てる |
| 見本の報告（鍵が無い時） | 見本の台帳で、エージェント（版7）を実際に回した結果をそのまま保存した `agent/sample_run.json` | 鍵の無い人にも本物の報告を見てもらうため。手では書いていない |

残す・戻すを決めるのは、どの Claude でもなくコードの決まりです（報告の形・検算の一致・両方の台帳で採点に合格・中身の確かめをすべて満たし、前の版より良い時だけ残す）。本番に使うかは人が画面で押して決めます。

**実際に起きたこと**（見本の2つの台帳で、分析担当の見直しを本物で2回回した）

1. 1回目：Opus は「書く量」「進め方」「集計の決まり」の3か所を直した。採点の回は減ったが、直した版は仕掛けなしの台帳で「3日以上先の予約に来店未記録が多かった」と、前の版が添えていた「偶然の差の可能性もあります」を外して言い切った。Sonnet の確かめが落とし、コードの決まりで**戻した**
2. 2回目：Opus は1回目の戻した理由を読み、「前回は調べ方のページまで書き換えて調べる手が縮んだので、今回はそのページには触れない」として「書く量」だけを直した。採点に合格した回は、台帳A が3回目 → 1回目、台帳B が3回で通らず → 2回目。中身の確かめは両方とも通り、費用は $2.32 → $1.83 で**残した**（本番に使うかは、人がまだ決めていない）

ここで言う「良くなった」は、この2つの見本の台帳と決めた物差しでの話です。ほかの台帳で良くなったことまでは確かめていません。

### 開発の中の Claude Code

アプリのコードは Claude Code が書きました。人が決めたのは、何を作るか・どちらにするか・お金をかけて回すかです。

| 人が決めたこと | Claude Code がしたこと |
|---|---|
| 作品の芯と名前・作る範囲（1店舗・チラシと LINE） | 設計書を書き、決まりどおりに実装した（FastAPI・SQLite・画面）。決めかねる所は2〜3案にして聞いた |
| 見本の数字の傾き（仕掛けは1つ・天候は入れない など）を選択肢から選んだ | 乱数の種を固定した見本の台帳の生成と、数が狙いどおりかの確かめの集計を書いて回した |
| 鍵の発行・置き場所・使う上限、本物の分析を回すか（1回ごと） | 鍵の中身を見ずにエージェントを作り、分析を回し、費用をセッションの使用量で確かめた |
| 現場の言葉で直すこと（「技術者向けの言葉が多い」「クーポンを使ったか分からない」など） | 画面と報告の見せ方を作り直し、写しの台帳で API を呼び、画面を撮って確かめた |
| 批判を受けてどこまで直すか | 指摘を「直す／直さない／確かめが要る」に分け、「無い」と言われた所は実物で確かめてから直した |

使った道具（BUILD_LOG に記録があるもの）：

- **advisor（Fable 5.1）**：方針を決める前に相談した。例：見本の報告は手で書かず本物の実行の結果だけを使う／報告の長さを決めているのは採点の基準／前回と今を日付ではなく「前回の分析の時点」で比べる
- **サブエージェント**：過去の入賞作の README を読ませ、書き方の型を出させた
- **スキル**：`claude-api`（Managed Agents の使い方を確かめてから書いた）・`dataviz`（効果の画面のグラフと数字の札）
- **Codex に批判をさせた**（判断と直しは Claude Code）：審査員役と店長役で、範囲を決める時（審査員役 27 → 39点）・作りかけの時（54 → 58点）・一本通った後（64 → 67点）
- **開始前に作ったもの（リポジトリには入れていない）**：push の前の点検 `publish-check`（勤務先の名前・鍵・個人情報の形を、ファイルと全コミットで探す）と、git の pre-commit フック（個人の noreply 以外のメール・`.env`・鍵らしい文字列のコミットを止める）
