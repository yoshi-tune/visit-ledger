# ナットク台帳

> チラシや LINE を見た人が、本当に店に来たのか。来店までを1本の台帳でつなぎ、Claude が台帳を掘って「次の一手」まで出す、地域の店のための台帳です。

- **困りごと**：地域の店は、チラシや LINE を見た人が本当に来店したか・クーポンが使われたかが分からず、効果の読み解きも人まかせ
- **すること**：LP → 予約 → 受付での来店・クーポンの記録を1本の台帳でつなぎ、施策ごとに何件が来店まで進んだかを数える
- **Claude が担うところ**：分析担当（Managed Agents）が台帳を自分で数え直して見立てと次の一手を出し、自分のやり方の直しも、見本の台帳2つで確かめながら2回試した（使うかは人が決める）

見本のデータで作った試作です。はじめの設定の後、DX 担当が毎回集計と読み解きを代わりにやらなくても、店長が分析を起こし、提案された対象を確かめて受付へ渡せる形を目指しました（店長だけで回せるかは、実際の店ではまだ確かめていません）。最初の対象は、チラシ・LINE からのネット予約を、このアプリの LP と予約の枠で受けられる店です（今の電話予約や予約帳とは自動ではそろいません）。店長が施策ごとの来店の記録を見て、次に試す対象を受付の一覧へ渡すところまでを作りました。実際の店での時間の短縮・来店の増加は、まだ測っていません。

ハッカソンの後も、チラシや LINE で集客している地域の店の店長が、月初のふり返りで「先月の施策から何件が来店まで進んだか・次に何を確かめるか」を自分で出せるようにします。分析の呼び出しは1か所で切り替える形（Managed Agents か、Messages API を1回か）にしてあり、どちらも同じ形（JSON Schema）の報告を返します（Messages API の形では、実行したスクリプトの記録が無いので、その分の検査は省きます）。ほかの基盤に移すことは、まだ試していません。

## なぜ作ったか

全社の DX 担当として、店のチラシや LINE の効果を、UTM を付けて GA4・Clarity で計り、Looker Studio にまとめてマネージャー会議に出してきました。けれど計れるのは Web の上の「見られた・押された」まで。予約と来店は店の側の記録で、チラシを見た人が本当に来店したかは分かりません。LP にはクーポンのボタンもありますが、店で使われたかも分かりません。3ページに並んだ数字から「なぜか・次に何をするか」を読み解くのも、見る人まかせになっています。

ナットク台帳は、チラシや LINE から来店までを1本の台帳でつなぎます。Claude（Managed Agents の分析エージェント）が台帳を自分で数え直して見立てを確かめ、次の一手と見る数字まで出します。次の分析は、その一手のその後を振り返ります。DX 担当が毎回の集計と読み解きを代わりにやらなくても、店長が自分で回せる形を目指しています（受付での入力・伝票との照らし合わせ・お客様への連絡は、人の仕事のまま残ります）。

DX 担当として作りたかったのは、担当が毎回数字を読み解かなくても、店の中で月初のふり返りが回る仕組みです。現場で困ってきたことを、次のように作りに入れました。

| 現場で困ってきたこと | この作品での判断 |
|---|---|
| Web の反応（GA4・Clarity）と、店の予約・来店の記録が別々で、つながらない | 同じ LP の閲覧の記録から、予約・来店・クーポンをつなぐ |
| 来店の記録が無いだけでは「来なかった」と言えない（押し忘れ・電話での変更がある） | 「来店未記録」と書く。分析には「来なかった」と断定しないよう指示し、採点の基準で点検する |
| 次の一手を決めても、店で実際にやったかが残らない | 一手を受付の一覧にし、「送った・返事あり」を受付で記録して、次の分析が読む |

**人の承認つきのループ**（[docs/LOOP.md](docs/LOOP.md)）：効果の画面の「月初のふり返りを回す」を押すと、Claude が台帳を数え直して次の一手を出し、終わるとナットク（Claude）がその一手から受付のタブの提案まで自動で作ります。人がするのは、分析が求めた対象と、提案された条件・一覧が合っているかを確かめて反映するか決めることと、受付での照らし合わせ・記録です（タブの条件の形はコードで検査しますが、分析の意図と合っているかは検査できないので、人が確かめます）。次の月の分析が、その記録で前回の一手を振り返ります（公開 URL で本物で確かめたのは、分析 → 自動の提案 → 人の反映までです）。自動で進むのは提案まで。分析のやり方の見直しはこのループに入れていません。新しい施策（チラシ・LINE の URL と QR）は、店長が店の設定の画面で足せます。はじめの設定（置き場所・鍵・費用の上限）は、まだ DX 担当がやります。同じ形をほかの業務のシステムに持ち込む時に差し替える所も、この文書にまとめました（移したことはまだありません）。

（店・お客様・数字はすべて見本です。実在の店のデータは入っていません。）

### 手元で起動する

必要なもの：Git と [uv](https://docs.astral.sh/uv/)（Python は uv が用意します）。Windows・Mac・Linux で同じ手順です。

手元の起動は `127.0.0.1`（その PC の中だけ）で待ち受けます。チラシの QR やクーポンの QR を別のスマホで読んでもつながらないので、**同じ PC のブラウザーで試してください**（LP はスマホ向けの画面ですが PC でも開けます。クーポンは QR の代わりに番号を受付の画面に入れます）。

```sh
git clone https://github.com/yoshi-tune/visit-ledger.git
cd visit-ledger
uv run uvicorn app.main:app              # http://127.0.0.1:8000/ を開く
```

初めての起動で、見本の台帳 `data/ledger.db` を自動で作ります（乱数の種を固定しているので、誰が作っても同じ中身）。台帳を作り直す時は `uv run python scripts/make_sample.py` を回してください。

**鍵が無くても最後まで試せます。** 鍵が無い時、Claude を呼ぶ所は「作者が見本の台帳で本物を回した時の結果」を保存したものを出します（手では書いていません）。

| 操作 | 鍵が無い時 |
|---|---|
| 予約・受付での来店・クーポン・お知らせの記録 | 手元の台帳に本当に記録する |
| 効果の画面 | 手元の台帳をその場で数える |
| 分析を頼む | 見本の報告（作ったばかりの見本の台帳で回した分析）を出す。**さっき足した予約・来店は、見本の報告には入りません** |
| ナットクに頼む（受付のタブ） | 依頼の文に関わらず、保存した見本の提案（明日の予約で8日以上）を出す。条件に合う件数と一覧は、手元の台帳で数える |
| 分析担当の見直し | 作者が本物で2回回した記録を見る |
| 分析への続けての質問 | できない |

デモ動画に映る分析は、鍵を入れて API で実際に回し、台帳に保存した分析の結果を開いたものです。

本物の分析も試す場合（任意。1回 $1 前後・4〜7分かかります）。起動中のサーバーは Ctrl+C で止めてから、鍵を入れて起動し直してください：

## 使い方

アプリの「今日」は **2026-11-07** に固定しています（見本データと時計をそろえるため）。

1. **LP**（スマホ向け）：<http://127.0.0.1:8000/lp/S-EKI?campaign=autumn_check_202610&src=flyer> を開き、「空いている日時を見る」
2. **予約**：メニュー → 日にち（今日 11/7 を選ぶ）→ 空いている時間 → 名前・電話（見本の値で可）→ 確認。送った時点で予約が確定し、予約番号が出る
3. **受付**：<http://127.0.0.1:8000/desk> の「今日の予約」で「来店」
4. **効果の画面**（ダッシュボード）：<http://127.0.0.1:8000/dashboard> で、上の数字の札（チラシ／LINE）と「来店までの道のり」の図が変わったことを見る。右の「Claude の見立て」に、いちばん新しい分析の次の一手が出る。「月初のふり返りを回す」を開いて「分析を頼む」を押すと、報告が新しいタブに出る
5. **次の一手が受付の仕事になる**：分析が終わると、ナットク（Claude）がその次の一手から受付のタブの提案を自動で作る。効果の画面の「Claude の見立て」に「人の番です」と出るので、次の一手の画面で、分析が求めた対象と、提案された条件・アプリが今の台帳で数えた一覧が合っているかを確かめ、合っていれば「反映する」（合わなければ「やめる」で、依頼の文を直して頼み直す）→ 受付に出たタブで記録する。分析の画面の「ナットクに頼む」から、手で依頼を書いて頼むこともできる。鍵が無い時は保存した見本の提案を使い、対象の一覧だけを手元の台帳で数えます（見本の提案は「明日の予約で8日以上」で固定なので、見本の報告の次の一手「来店未記録の確かめ」とは合いません。見比べて頼み直す流れは、公開 URL の保存済みの分析か、鍵を入れた時に見てください）。部品・取り消し・記録の決まりは [docs/MAINTENANCE.md](docs/MAINTENANCE.md)・[docs/LOOP.md](docs/LOOP.md)

ここまでが主な流れ（配る → 見る → 予約する → 来る → 効果が分かる → 次の一手を受付の仕事にする）です。ほかにも次の画面があります：

- **店の設定**：<http://127.0.0.1:8000/settings> で時間帯ごとの台数・休みの曜日・休みの日を変えると、予約の画面にすぐ反映される（見本の初期値：10〜16時の6枠に各2台・毎週水曜は休み）
- **施策を始める**：同じ店の設定の画面の上で、キャンペーンの名前・期間・媒体（チラシ／LINE）・配る数を入れると、媒体ごとの LP の URL と QR が出る。その URL から開いた人の予約・来店は、効果の画面でキャンペーンを選んで見られ、分析とループにもそのまま入る
- **クーポン**：LP の「クーポン（点検 ¥500 引き）」で QR と番号が出る。受付の <http://127.0.0.1:8000/desk/coupon> に番号を入れる（店のスマホで QR を読むと同じ画面が開く）。予約のある人は「来店とクーポンを記録する」の1回で来店とクーポンが台帳に残り、予約の無い人は「予約なしの来店」として残る。効果の画面のクーポンの欄が変わる。間違えて押した「使った」は、同じ画面で取り消せる（取り消した記録も台帳に残る）
- **分析担当の見直し**：<http://127.0.0.1:8000/improve> で、分析担当（AI）が自分の仕事のやり方を直した案と、届く報告の前と後・確かめた結果を見る。本番に使うかは人が押して決める。台帳に見直しの記録が無い時（鍵が無い手元の起動など）は、作者が本物で2回回した時の記録を「見本の記録」として出す（仕組みは [docs/IMPROVE.md](docs/IMPROVE.md)）

## 業務の守りと、まだ守れていない範囲

Claude に台帳を読ませ、受付の仕事まで変えさせるので、コードで止める所と、止めていない所を分けて書きます。

- **渡すものを絞る**：分析に渡す CSV は、許可した列だけを書き出します（[app/export.py](app/export.py)。名前・電話・担当・クーポンの番号は、許可の表を書き換えても出ない柵付き）。予約番号と閲覧の番号は書き出すたびに仮の番号に置き換え、対応表はアプリの中にだけ置きます。分析の箱は Web の検索・取得を切り、通信を制限しています。ただし CSV は Anthropic の箱に送っています。依頼の文や質問に人が書いた個人情報を、もれなく取り除く仕組みはありません（分析への質問は電話番号らしい10桁以上の数字の並びを断りますが、名前は見分けられないので、画面で「お客様の名前・電話を書かない」と頼んでいます）
- **報告を検査する**：報告は決めた形（JSON Schema）に合わなければ失敗にします。項目の数の上限や、報告が引用したスクリプト名が道具の実行の記録に見当たらない時などは、注意として記録します（実行が成功したか・計算が正しいかまでは確かめません）（[app/analysis/__init__.py](app/analysis/__init__.py)）。アプリの集計と数え直しが合うかは Claude が確かめて報告に書き、採点の基準で最大3回まで書き直させます。数字と結論の正しさを、コードがすべて保証するものではありません
- **言い過ぎを点検する**：アプリの画面は、記録の無い予約を「来なかった」ではなく「来店未記録」、お知らせの記録が無い予約を「送らなかった」ではなく「送信記録なし」と出します。分析には、この断定や「差を施策の効果と言い切る」ことを避けるよう指示し、採点の基準 `agent/rubric.md` で点検します（出力を必ず止めるものではありません）
- **変えてよい範囲を決める**：受付のタブの提案は、決まった部品と値の範囲だけ。外れた案はコードで捨て（[app/maintenance.py](app/maintenance.py)）、件数と一覧はアプリが数えます。反映するのは人が「反映する」を押した時だけで、設定は版ごとに残り、「さっきの変更を取り消す」で戻せます（お知らせの記録は消えません）。押し間違えたお知らせ・クーポンの記録も取り消せ、取り消した記録は別の表に残ります
- **公開 URL のログインと全体の上限**（公開版だけ）：お客様向けの画面（LP・予約・お客様のクーポン）としくみの説明を除き、店の画面と API は、テスト用の ID でログインした人だけが開けます（[app/public.py](app/public.py)。ログインしていないと API は 401）。鍵は置き場所の環境変数にだけ置きます。Claude に使う額は、Anthropic Console のワークスペースの月の上限（$20）と、アプリの側の上限（台帳に残った費用と動いている分析の見込みの合計が上限に近ければ見本に切り替える・本物の分析は一度に1つまで）の2段で止めます。アプリの側は分析が終わってから額を数えるので、本当の歯止めは Console の上限です。思わぬ失敗は、中身を出さずに決まった文だけを返します
- **まだできていないこと**：ログインはテスト用の ID 1つだけで、店の人ごとの権限（店長・スタッフ）はありません。手元で起動した時はログインはありません。お知らせは実際には送りません。見本の台帳で試す段階で、実際の店での効果は確かめていません

## この台帳で分かること・分からないこと

- **追えるのは、施策の URL（チラシの QR・LINE のリンク）から LP を開いた所から。** 配った紙を誰が受け取ったかは追いません。配った数は参考の値です
- **予約・クーポンを結ぶのは、同じ LP の閲覧の記録（同じスマホ・同じブラウザー）。** 同じ人かどうかは確かめていません。電話で予約した人や、別のスマホでクーポンを見せた人は「予約なしの来店」に見えます
- **予約の枠は、ネット予約の枠です。** 電話の予約や今の予約帳とは自動ではそろわないので、分けて使う前提です（例：ネット予約は各時間1台まで）。整備の中身ごとの作業時間は見ていません
- **来店未記録の予約を受付で「取消（来なかった・電話で取消）」にすると、来店率の分母から外れます。** 来店率は「来店 ÷（来店＋来店未記録）」で、取消は入れないためです。受付で確かめた後に来店率が上がった時は、来店を記録した分か、取消にして分母から外れた分かを、件数で見分けてください
- **割引で得をしたか・利益・施策をやらなかった時と比べて増えた分は、測っていません。** 分かるのは、施策ごとの「LP → 予約 → 来店 → クーポン」の数と、その読み解きです
- **前回の一手の振り返り**は、数字の変化を一手の効果とは言いません。受付で付けたお知らせの記録（送った・返事あり、記録のある予約の日時を変えると「日時を変えた」も自動で残る）は台帳に残り、次の分析が「送信記録あり／送信記録なし／うち返事あり」の来店率を並べます。これは**今の条件で数え直した参考の集計**で、連絡した時の対象を固定して追ったものではありません（連絡の後に日時を変えた予約は、条件から外れることがある）。記録が無いのは「送らなかった」ではなく「送信の記録が無い」です（外で送って記録し忘れたかもしれない）。並べるのは観測までで、記録のある人と無い人はもともと連絡のつきやすさが違うかもしれないので「お知らせが効いた」とは言いません。件数が少ないうち・来店予定日がまだ来ていないうちは「まだ判断できない」と書きます。タブを使わずにやった一手（電話・伝票との照らし合わせなど）は、今も台帳に残りません
- **分析担当の見直しで「良くなった」**のは、答えの分かっている2つの見本の台帳と、決めた物差しでの話です。ほかの台帳や本物の店で良くなったことまでは確かめていません
- **店の人ごとの権限（店長・スタッフ）はまだありません。** 公開 URL はテスト用の ID 1つでのログイン、手元の起動はログインなしです

## Claude の使い方

**開発の一例：クーポン**（人の話から Claude Code が作り、確かめ、批判を受けて直した流れ。BUILD_LOG 11/2・11/3、コミット [0c18ac6](https://github.com/yoshi-tune/visit-ledger/commit/0c18ac6)・[7171153](https://github.com/yoshi-tune/visit-ledger/commit/7171153)。開発の分担は[下](#開発の中の-claude-code)）

1. 人が話した：「LP にクーポンのボタンだけがあって、店で使われたかが分からない」。予約なしの来店まで追う・見本の数字に傾きを付けない、を選んだ
2. Claude Code が advisor と決めて作った：QR の中身は URL だけ・開いただけでは記録しない・予約は閲覧の記録で結ぶ（受付に選ばせない）。効果の画面にクーポンの欄、分析に渡す CSV にクーポンの表（番号は落とす）、採点の基準に「クーポンの利用率を効果と書かない」
3. 確かめた：見本の台帳の前からの数字22項目が変わらないこと、同じ閲覧は同じ番号・2回目の使用を断る・知らない番号は 404、を API で見た
4. Codex の批判（審査員役・店長役）の後に人が選び、来店とクーポンを1回で記録する形と、押し間違えた「使った」の取り消し（取り消した記録も残す）を足した

**実際に起きたこと**：分析担当（AI）に自分の仕事のやり方を2回直させました。1回目の直しは、差の無い見本の台帳で「偶然の差の可能性もあります」という断りを外して言い切ったので、別の Claude の確かめが落とし、コードの決まりで戻しました。2回目は、直す役がその理由を読んで直し方を変え（調べ方には触れず、書く量だけを直す）、採点に合格するまでが短くなったので残しました。人が本番に使うと決めました（その後、人がお知らせの記録を読む決まりを足して版9、11/4 に記録の呼び方を「送信記録あり／なし／うち返事あり」に直して、今の分析担当は版10。詳しくは下）。

アプリが数えるのは「何件か」まで。**「なぜか・次に何をするか」を読み解くのが、作品の中の Claude の仕事**です。その読み解きのやり方の直しも、人が始めて、見本の台帳2つで確かめながら2回試しました（ほかの台帳で良くなるかは確かめていません）。

### 作品の中の Claude

| 役 | モデル・機能 | なぜそれにしたか |
|---|---|---|
| **分析担当**（効果の画面の「分析を頼む」） | **Managed Agents**（既定 Opus 5.5。Sonnet 5.5・Haiku 5.5 も選べる）。サンドボックスでコードを書いて実行する | 数字を文章で推し量らせず、台帳の書き出し（CSV）を自分で数え直させるため。集計1回ごとに `step_NN.py` を書いて実行し、その数字だけを報告に使う |
| 　└ 渡すものを絞る | Web の検索・取得を切り、通信を制限した環境（`networking: limited`）。渡すのは許可した列だけの CSV（番号は仮の番号に置き換え）と、アプリの集計だけ | お客様の名前・電話を分析に渡さないため（列を絞るのは書き出しの関数1か所）。CSV そのものは Anthropic の箱に送る |
| 　└ 基準でやり直す | outcomes（`define_outcome`）に採点の基準 `agent/rubric.md` を渡し、最大3回までやり直す | 検算の一致・件数が少ない時の断り・「効果と言い切らない」などを、エージェントが自分で満たすまで直させるため |
| 　└ 使い過ぎない | 1回の上限額（既定 $3.00、`VL_BUDGET_CENTS`）を超えたら止める | 思わぬ費用を防ぐため。分析ごとの費用の目安は、分析の画面と効果の画面に出す |
| 　└ 続けて質問 | 終えた分析と同じセッションに質問を送る（`chat_NN.py` で数え直して答える） | 前の集計と CSV が残った作業場所で、そのまま掘り下げられるため |
| 　└ 前回を振り返る | 前回の「次の一手」と、その時の集計を `previous.json` で渡す | 次の分析が、前回の一手のその後を数え直すため（記録の直しと新しい予約・来店を分け、一手の効果とは言い切らない） |
| 予備の形 | Messages API を1回（`VL_ANALYSIS_MODE=messages`）。同じ報告の形（JSON Schema）で返す | Managed Agents が使えない時でも、同じ画面に報告を出すため |
| **分析担当の手順書を直す役**（[docs/IMPROVE.md](docs/IMPROVE.md)） | Opus 5.5（`effort: high`・JSON Schema の出力） | 採点で直しを求められた理由と前の回の結果を読み、手順書の1〜3か所を直す。直してはいけない節（数え方・言わないこと・報告の形）に触れた案は、コードで捨てる |
| **中身を確かめる役** | Sonnet 5.5 と、決まった問い `agent/judge.md`（直す役からは変えられない） | 仕掛けありの台帳で本当の理由（予約から来店予定日までの日数）を見つけたか、仕掛けなしの台帳で偶然かもしれない差を言い切らなかったかを、毎回同じ問いで確かめるため |
| **言い直し役** | Sonnet 5.5（断られた時は Opus 5.5 で聞き直す） | 直しの説明を、店長の言葉と「届く報告の前と後」にするため。抜き出した文が本当に報告にあるかはコードで確かめ、無ければ捨てる |
| **受付のタブを提案する役**（「ナットクに頼む」） | Sonnet 5.5（JSON Schema の出力）。渡すのは今のタブ・部品の一覧・依頼の文だけ | 決まった部品を組み合わせるだけの仕事なので。台帳の行・名前・電話の列は渡さない（ただし依頼の文はそのまま渡すので、画面に「お客様の名前・電話を書かない」と出している）。部品から外れた案（知らない条件・範囲外の値・SQL らしい名前）はコードで捨て、件数と一覧はアプリが数える。反映するかは人が押して決める |
| 見本の報告・見本の提案（鍵が無い時） | 見本の台帳で、エージェント（版9）を実際に回した結果をそのまま保存した `agent/sample_run.json` と、Sonnet に実際に提案させた `agent/sample_proposal.json`、見直しを本物で2回回した記録を画面に出す形で保存した `agent/sample_improvements.json` | 鍵の無い人にも本物の報告を見てもらうため。手では書いていない |

Messages API で呼ぶ役（予備の形・直す役・確かめる役・言い直し役・タブを提案する役）には、サーバー側の予備のモデル（`server-side-fallback`）を付けています。表のモデルが答えられない時は、別のモデルが答えることがあります。

残す・戻すを決めるのは、どの Claude でもなくコードの決まりです（報告の形・報告に書かれた検算の一致・両方の台帳で採点に合格・中身の確かめをすべて満たし、前の版より良い時だけ残す）。本番に使うかは人が画面で押して決めます。

**実際に起きたこと**（見本の2つの台帳で、分析担当の見直しを本物で2回回した）

1. 1回目：Opus は「書く量」「進め方」「集計の決まり」の3か所を直した。採点の回は減ったが、直した版は仕掛けなしの台帳で「3日以上先の予約に来店未記録が多かった」と、前の版が添えていた「偶然の差の可能性もあります」を外して言い切った。Sonnet の確かめが落とし、コードの決まりで**戻した**
2. 2回目：Opus は1回目の戻した理由を読み、「前回は調べ方のページまで書き換えて調べる手が縮んだので、今回はそのページには触れない」として「書く量」だけを直した。採点に合格した回は、台帳A が3回目 → 1回目、台帳B が3回で通らず → 2回目。中身の確かめは両方とも通り、費用は $2.32 → $1.83 で**残した**
3. 人が画面で「この版を本番に使う」を押し、分析担当は版8になった。作ったばかりの見本の台帳で版8を回すと、採点の1回目で合格し（版7は3回目）、4分50秒・$0.99。数え直しの欄は「来店87件・来店未記録23件」の入った1文になり、見立ての「日数が原因とは言い切れない」という断りも残った

ここで言う「良くなった」は、この2つの見本の台帳と決めた物差しでの話です。ほかの台帳で良くなったことまでは確かめていません。

### 開発の中の Claude Code

アプリのコードは Claude Code が書きました。人が決めたのは、何を作るか・どちらにするか・お金をかけて回すかです。

| 人が決めたこと | Claude Code がしたこと |
|---|---|
| 作品の芯と名前・作る範囲（1店舗・チラシと LINE） | 設計書を書き、決まりどおりに実装した（FastAPI・SQLite・画面）。決めかねる所は2〜3案にして聞いた |
| 見本の数字の傾き（仕掛けは1つ・天候は入れない など）を選択肢から選んだ | 乱数の種を固定した見本の台帳の生成と、数が狙いどおりかの確かめの集計を書いて回した |
| 鍵の発行・置き場所・使う上限、本物の分析を回すか（1回ごと） | 鍵の中身を見ずにエージェントを作り、分析を回し、費用をセッションの使用量で確かめた |
| 現場の言葉で直すこと（「技術者向けの言葉が多い」「クーポンを使ったか分からない」など） | 画面と報告の見せ方を作り直し、写しの台帳で API を呼び、画面を撮って確かめた |
| 批判を受けてどこまで直すか | 指摘を「直す／直さない／確かめが要る」に分け、「無い」と言われた所は実物で確かめてから直した |

使った道具（BUILD_LOG に記録があるもの）：

- **advisor（Fable 5.1）**：方針を決める前に相談した。例：見本の報告は手で書かず本物の実行の結果だけを使う／報告の長さを決めているのは採点の基準／前回と今を日付ではなく「前回の分析の時点」で比べる
- **サブエージェント**：過去の入賞作の README を読ませ、書き方の型を出させた
- **スキル**：`claude-api`（Managed Agents の使い方を確かめてから書いた）・`dataviz`（効果の画面のグラフと数字の札）
- **Codex に批判をさせた**（判断と直しは Claude Code）：審査員役と店長役で、範囲を決める時（審査員役 27 → 39点）・作りかけの時（54 → 58点）・一本通った後（64 → 67点）・デモ動画を一度通した後（72 → 68点。言い過ぎの直し残しと、記録の訂正・比べる相手の固定が無いことで下がり、記録の訂正は直した）
- **開始前に作ったもの（リポジトリには入れていない）**：push の前の点検 `publish-check`（勤務先の名前・鍵・個人情報の形を、ファイルと全コミットで探す）と、git の pre-commit フック（個人の noreply 以外のメール・`.env`・鍵らしい文字列のコミットを止める）
