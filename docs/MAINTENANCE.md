# 構想：ナットクに頼むメンテナンス

> 2026-11-02 の構想（まだ作っていない）。
> 決めたこと（11/2）：段階 A を作り、段階 B も試作する／分析の「次の一手」からつなげる／権限を設ける。

## 1. ねらい

分析エージェントが「次の一手」を出しても、今は店長がそれを覚えておき、自分でやり方を変えるしかない。
ツールの側は先月と同じままなので、次の一手を試したかどうかも台帳に残らない。

このツールを長く使ってもらうには、**ツールそのものが店に合わせて変わっていく**必要がある。
そこで、店長が受付や効果の画面から「ナットクに頼む」と、Claude が直し方を提案し、店長が押せば反映される仕組みを作る。

ナットクの役割は2つになる。

| 役割 | 何をするか |
|---|---|
| 数字で納得 | 分析：台帳を調べて、次の一手を出す（作ってある） |
| 直して納得 | メンテナンス：次の一手や店の声を受けて、ツールを直す（この構想） |

## 2. 改善のループ（芯）

```
分析の報告 ── 次の一手「8日以上先の予約に、前日に確認の電話をする」
   │  「ナットクに頼む」を押す（依頼の文は下書き済み）
   ▼
メンテナンスの画面（チャット）
   │  ナットク：受付に「前日に確認する予約」のタブを足す案を出す（変更点と見本の画面）
   ▼
店長が「反映」を押す ── 設定の新しい版として保存（いつでも戻せる）
   ▼
受付に新しいタブが出る ── 毎朝、前日確認の電話をする（誰がいつ電話したかも残る）
   ▼
翌月の分析 ── 「前日確認をした予約」と「しなかった予約」の来店率を比べる
```

ありきたりにしないための要は、**分析 → ツールの変更 → 効果の確かめ が、同じ台帳の上で一周する**こと。
ツールの変更は、どの分析の、どの次の一手から来たかを記録する。翌月の分析では、それを手がかりに効いたかを確かめる。

## 3. 2つの段階

| 段階 | 変えられるもの | しくみ | 今週 |
|---|---|---|---|
| **A：設定の変更** | 時間帯・メニュー・文言・施策・受付のタブ（条件で決める一覧） | Messages API に「変更の操作」を道具として渡し、Claude が操作の組み合わせを提案する。アプリが検査して見本を出し、店長が反映する | **作る候補** |
| **B：機能の変更** | 画面やロジックそのもの | Managed Agents にリポジトリを渡し、サンドボックスで直してテストを回し、プルリクエストを出す。作り手が見て取り込む | **試作**（プルリクエストを出すところまで） |

段階 A は、決められた操作しかできないので安全で、確かめやすい。
段階 B は自由だが、鍵の扱い・レビュー・失敗した時の戻し方が要る。今週は「依頼からプルリクエストが出るまで」を試作し、取り込みは作り手が GitHub で行う。

## 4. 段階 A：変更の操作（許可するものだけ）

| 操作 | 例 | 検査 |
|---|---|---|
| `add_slot` / `remove_slot` | 「17時も選べるように」 | 時刻の形・重なり |
| `add_menu` / `rename_menu` | 「車検の相談を足して」 | 名前の重なり。名前を変えても過去の予約は元の名前のまま |
| `set_copy` | LP の見出し・完了画面・ナットクのひと言 | 長さ・個人情報らしき文字が無いか |
| `add_campaign` | 「12月のチラシ（3000枚）を足して」 | 施策コードの形 `{メニュー}_{YYYYMM}`・期間 |
| `add_desk_tab` | 「前日に確認する予約の一覧」 | 条件は決まった部品の組み合わせだけ（状態・確定日が◯日後・メニュー・媒体）。SQL は書かせない |
| `add_checkbox` | 受付のカードに「前日確認した」を付ける | 押した記録は台帳の履歴に残す |

**変えられないもの**：漏斗と来店率の数え方（設計書 §3）、個人情報の扱い、台帳の記録そのもの。
数え方が黙って変わると、先月と今月の数字が比べられなくなるため。数え方を変えたい依頼には、「それは作り手への相談です」と答える。

## 5. 守ること

- Claude に渡すのは、**今の設定と画面の定義だけ**。台帳の行・名前・電話は渡さない（分析と同じ線引き）
- 変更は必ず「提案 → 見本 → 反映の権限がある人が反映 → 版として保存 → いつでも戻せる」の順。勝手には反映しない（§10 の権限）
- 変更の記録：誰が・いつ・どの依頼で・どの分析の次の一手から・何を変えたか
- 1回の依頼で使う量に上限を付ける

## 6. データの形（追加）

| 表 | 列 |
|---|---|
| `settings_versions` | `version`, `created_at`, `settings_json`, `change_request_id` |
| `change_requests` | `id`, `created_at`, `requested_by`, `role`, `kind`（settings / code）, `text`, `source_analysis_id`, `proposal_json`, `status`（proposed / applied / rejected / rolled_back / pr_opened）, `applied_version`, `applied_by`, `pr_url` |
| `staff` | `staff_id`, `name`（見本）, `role`（owner / staff / developer）, `pin_hash` |

アプリは、メニュー・時間帯・文言・受付のタブを、コードの定数ではなく最新の `settings_versions` から読むように変える。
## 7. 会話の見本

> **店長**（分析の「次の一手」から「ナットクに頼む」を押す。依頼の文は下書き済み）
> 8日以上先の予約に、前日に確認の電話をしたい。受付で分かるようにして。
>
> **ナットク**
> こう直すのはどうでしょう。
> ① 受付に「前日確認」のタブを足す（条件：確定済み・確定日が明日）
> ② そのタブのカードに「確認の電話をした」のチェックを付ける（押した記録は台帳に残ります）
> 数え方は変わりません。下の見本で見え方を確かめてから「反映」を押してください。
> ［見本：受付の画面に「前日確認 3件」のタブ］ ［反映する］ ［やめる］
>
> **店長**：反映
>
> **ナットク**
> きゅっ。反映しました（設定の版 4）。元に戻したい時は「版 3 に戻す」を押してください。
> 来月の分析では、確認の電話をした予約としなかった予約の来店率を比べますね。

## 8. デモでの見せ方（案）

効果の画面の「次の一手」→「ナットクに頼む」→ 提案と見本 → 反映 → 受付に新しいタブが出る、を20〜30秒で見せる。
3分の配分のうち、LP と予約の入力の時間を縮めて、この場面に回す。

## 9. 作る量と日程への影響（段階 A の最小の形）

| 作るもの | 目安 |
|---|---|
| 設定を表に移す（メニュー・時間帯・文言）＋版と戻し | 1〜1.5時間 |
| メンテナンスの画面（チャット・提案・見本・反映） | 1.5〜2時間 |
| Claude の呼び出し（操作を道具として渡す・検査） | 1時間 |
| 受付のタブを条件で足す仕組み＋チェック | 1時間 |
| 次の一手からの「ナットクに頼む」 | 0.5時間 |

合わせて5〜6時間。平日の1時間の枠だけでは収まらないので、11/7 の午前を使うことになる。
11/3 の分析エージェントの初めての実行（同じ鍵を使う）を先に済ませるのが前提。

## 10. 権限（決めたこと：権限を設ける）

| 役割 | 依頼する | 設定の変更を反映・戻す | コードの変更（段階 B）を頼む | プルリクエストを取り込む |
|---|:-:|:-:|:-:|:-:|
| スタッフ | ○ | × | × | × |
| 店長 | ○ | ○ | ○ | × |
| 作り手 | ○ | ○ | ○ | ○（GitHub で） |

- 受付・効果・メンテナンスの画面は、担当を選んで4桁の暗証番号で入る（見本の番号は README に書く。番号はハッシュで持つ）
- 受付の「担当 A/B」は、この入り方に置き換える。だれが確定・来店・反映したかが台帳に残る
- 権限の判定はサーバーで行う（画面のボタンを隠すだけにしない）
- 本番で使うなら、店の業務アプリの認証に置き換える前提（今回は見本の入り方）

## 11. 段階 B の試作（コードの変更）

1. 店長がチャットで、設定では届かない依頼をする（例：「来店の時にお客様の車の走行距離もメモしたい」）
2. ナットクが「これは設定では直せないので、作り手への変更の依頼にします」と答え、依頼の文をまとめる。店長が送る
3. Managed Agents のセッションにリポジトリを渡す。エージェントはブランチを切って直し、テスト（見本データの生成と漏斗の答え合わせ）を回し、プルリクエストを出す
4. アプリはプルリクエストの URL を `change_requests` に残し、画面に出す。取り込むかは作り手が GitHub で決める（アプリからは取り込まない）

- GitHub の鍵は Managed Agents の vault に置き、リポジトリにもアプリにも入れない
- エージェントには、設計書 §3（数え方）と §7（個人情報）を守る指示と、テストが通らなければプルリクエストを出さない決まりを渡す
- 作り手が取り込むまで、店の画面は何も変わらない（段階 A と違って、その場では直らないと画面で伝える）

## 12. 作る順番（案）

前提：11/3 に鍵を入れ、分析エージェントを初めて動かす（メンテナンスも同じ鍵を使う）。

| 順 | 作るもの | 確かめ方 |
|---|---|---|
| 1 | 権限（担当と暗証番号・サーバーでの判定） | 権限の無い操作が断られる |
| 2 | 設定を表に移す＋版と戻し | 見本データの漏斗が変わらない。戻すと元の画面になる |

| 5 | 次の一手からの「ナットクに頼む」 | 分析の報告から依頼の文が下書きされる |
| 6 | 段階 B の試作 | 見本の依頼でプルリクエストが出る |
