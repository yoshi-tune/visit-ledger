# 構想：ナットクに頼むメンテナンス

> 2026-11-02 の構想。**段階 A は 2026-11-03 に作った**（`app/maintenance.py`・画面「ナットクに頼む」`/maintenance`・受付の足したタブ・`reminders`）。
> 作っていないもの：権限（§9 の担当ごとの暗証番号と `staff` の表。今は受付と同じ「担当 A/B」を選ぶだけ）・段階 B・時間帯やメニューなどの変更。鍵が無い時は、本物の提案を保存した `agent/sample_proposal.json` を「見本の提案」として出す。
> 11/2 夜に予約の流れを「その場で確定」に切り替えたので、次の一手は「前日の電話」ではなく「前日のお知らせ（LINE・ショートメッセージ）」にした。
> 決めたこと（11/2 夜・Codex の臨時レビューの後）：**段階 A は「前日のお知らせの一覧とお知らせの記録」に絞って作る。段階 B（コードの変更）は構想にとどめる**。分析の「次の一手」からつなげる。権限を設ける。

## 1. ねらい

分析エージェントが「次の一手」を出しても、今は店長がそれを覚えておき、自分でやり方を変えるしかない。
ツールの側は先月と同じままなので、次の一手を試したかどうかも台帳に残らない。

このツールを長く使ってもらうには、**分析で出た一手が、そのまま翌朝の仕事になり、やった記録が次の分析に戻る**必要がある。
チャットで設定が変わること自体は目的ではない。「やるべき相手の一覧ができる → スタッフが送る → 結果が残る → 振り返れる」まで一周させる。

| ナットクの役割 | 何をするか |
|---|---|
| 数字で納得 | 分析：台帳を調べて、次の一手を出す |
| 直して納得 | メンテナンス：次の一手を受けて、受付に「やる相手の一覧」と「結果の記録」を足す（この構想） |

## 2. 改善のループ（芯）

```
分析の報告 ── 次の一手「予約を送ってから来店予定日まで8日以上ある予約に、前日にお知らせを送る」
   │  「ナットクに頼む」を押す（依頼の文は下書き済み）
   ▼
メンテナンスの画面（チャット）
   │  ナットク：受付に「前日のお知らせ」のタブを足す案を出す
   │  　条件：予約中 ・ 来店予定日が明日 ・ 予約を送ってから来店予定日まで8日以上
   │  　見本：「明日の確定予約 5件のうち、条件に合うのは 3件」と、その3件を出す
   ▼
人が「反映」を押す ── 設定の新しい版として保存（反映の権限の確かめは、まだ作っていない）
   ▼
受付に「前日のお知らせ 3件」のタブが出る ── お知らせの結果を残す（送った・返事あり。日時を変えると「日時を変えた」が自動で残る）
   ▼
次の分析 ── 同じ条件の予約の中で、送信記録あり／送信記録なし／うち返事あり の来店率を並べる
```

- 「8日以上」の数え方は設計書 §6 の仕込みと同じ：**予約を送った日から来店予定日までの日数**。日時を変えた予約は、変えた後の来店予定日で数える
- 次の分析で並べるのは観測まで。送信記録のある人と無い人は、もともと連絡のつきやすさが違うかもしれず、記録が無くても外で送って記録し忘れたかもしれないので、**「お知らせが効いた」とは言わない**。件数が少なければ「まだ判断できない」と書く
- 来店未記録が減っても、本当に来店が増えたのか、記録の押し忘れが減ったのかは区別できない。そのことも報告に書く

## 3. 段階 A：前日のお知らせの一覧とお知らせの記録（作る）

### 変更の操作（許可するのはこれだけ）

| 操作 | 中身 | 検査 |
|---|---|---|
| `add_desk_tab` | 受付に、条件で決まる一覧のタブを足す | 条件は決まった部品の組み合わせだけ：状態・来店予定日が今日から◯日後・予約を送ってから来店予定日までの日数・メニュー・媒体。SQL は書かせない |
| `remove_desk_tab` | 足したタブを外す | 外しても、そのタブで残したお知らせの記録は消さない |

時間帯・メニュー・文言・施策の変更は、今回は作らない（審査員役と店長役の指摘：広げると一周が間に合わない）。

### 見本の出し方

「版3に戻す」のような作り手の言葉ではなく、店長が判断できる形で出す。

- 「明日の確定予約 5件のうち、条件に合うのは 3件です」と、その3件のお客様の名前（受付の画面と同じ見え方）
- 条件を日本語で全部書く（予約中・来店予定日が明日・予約を送ってから8日以上）
- 取り消しは「さっきの変更を取り消す」。取り消しても、送った記録は消えない

### お知らせの記録

新しく `reminders` の表を作る（11/2 夜に、電話の記録 `contact_attempts` は予約の流れの切り替えで外した）。

| 結果 | 意味 |
|---|---|
| `sent` | お知らせを送った（今回は実際には送らず、送ったことだけ記録する見本） |
| `replied` | 返事があった（来店する・日時を変えたい など） |
| `rescheduled` | 日時を変えた（11/4 から、お知らせの記録がある予約の日時を受付の「日時を変える」で変えると、同じ取引で自動で残る。手で押すボタンは外した） |

記録には、どのタブ（どの変更）から送ったかを付け、次の分析の書き出しに含める（名前・電話・担当は含めない）。

## 4. 段階 B：機能の変更（構想だけ）

設定では直せない依頼（例：「来店の時に車の走行距離もメモしたい」）は、Managed Agents にリポジトリを渡して直させ、テストを回してプルリクエストを出す、という形が考えられる。
ただし、プルリクエストが出るだけでは店の仕事は変わらず、店長には「誰がいつ直してくれるか」が見えない。鍵の扱い・レビュー・戻し方も要る。
今回は作らず、README と動画で「この先」として触れるだけにする。

## 5. 守ること

- Claude に渡すのは、**今の設定と、条件に使える部品の一覧だけ**。台帳の行・名前・電話は渡さない（分析と同じ線引き）。見本の件数と名前は、アプリが手元で数えて画面に出す
- 変更は必ず「提案 → 見本 → 反映の権限がある人が反映 → 版として保存」の順。勝手には反映しない
- 来店までの道のりと来店率の数え方（設計書 §3）は変えられない
- 戻せるのは設定（タブ）だけ。送った記録、変更の後に入った予約は戻らない
- 変更の記録：誰が・いつ・どの依頼で・どの分析の次の一手から・何を変えたか
- 1回の依頼で使う量に上限を付ける

## 7. 会話の見本

> **店長**（分析の「次の一手」から「ナットクに頼む」を押す。依頼の文は下書き済み）
> 予約を送ってから来店予定日まで8日以上ある予約に、前日にお知らせを送りたい。受付で分かるようにして。
>
> **ナットク**
> こう直すのはどうでしょう。

> ・予約中　・来店予定日が明日　・予約を送ってから来店予定日まで8日以上

>

> 件数が少ないうちは「まだ判断できない」と書きます。

## 8. デモでの見せ方（案）

効果の画面の「次の一手」→「ナットクに頼む」→ 条件と見本（3件）→ 反映 → 受付に「前日のお知らせ」のタブ → 1件に「つながった」を記録、を40秒ほどで見せる。
翌月の振り返りは見本のデータで示し、「見本です」と明記する（本物の効果とは言わない）。

## 9. 権限

| 役割 | 依頼する | 反映する・取り消す | 受付の操作 |
|---|:-:|:-:|:-:|
| スタッフ | ○ | × | ○ |
| 店長 | ○ | ○ | ○ |

- 受付・効果・メンテナンスの画面は、担当を選んで4桁の暗証番号で入る（見本の番号は README に書く。番号はハッシュで持つ）
- 受付の「担当 A/B」は、この入り方に置き換える
- 権限の判定は API の側で行う。受付の一覧（名前・電話を含む）も、入った人にだけ返す
- 本番で使うなら、店の業務アプリの認証に置き換える前提（今回は見本の入り方）
