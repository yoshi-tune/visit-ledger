# 設計書（visit-ledger）

> 2026-11-02 版。Codex との1回目のディベート（審査員役・店長役、2往復）を受けて範囲を絞った。
> 出てくる店・数字・人はすべて見本。

## 1. 解きたい困りごと

舞台は **車の点検・整備を受け付ける地域の店**（オイル交換・タイヤ交換・点検など）。

見本の場面：月初、店長が先月のチラシと LINE 配信をふり返る。
チラシの枚数・LINE の配信数・ネット予約・電話での日程の調整・来店は、別々の画面や紙にある。
「チラシ経由の予約のうち、何件が実際に来店したか」は手で突き合わせないと分からず、
「チラシは効いていないのでは」という印象だけが残る。

visit-ledger は、施策の URL から予約の希望・店での確定・来店までを **1本の台帳** に記録し、
「その施策経由の予約が、どこまで進んだか」を施策ごとに見せる。
最後に Claude の分析エージェントが台帳を **自分で集計し直しながら** 調べ、
最初の見立てが追加の集計でどう変わったかと、店として次に確かめる一手を、数字の根拠を付けて報告する。

役割の分け方：**アプリは数える。エージェントは調べて確かめる。店長が決める。**

### 作品の芯

> 施策付きの予約1件が、店での確定を経て来店までつながる。その台帳を Claude が追加で集計し、
> 店長が「次に何を確かめるか」を1つ決められる。

これに効かないものは後回しにする。予算の配分（チラシをやめるか等）を決める道具ではない（§12）。

- 分析の基準（`as_of`）はこの「今日」の日付。来店待ち・来店未記録の判定は **すべて日付の単位で比べる**（時刻では比べない）

## 3. 流れと数え方

```
[施策] チラシ・LINE … URL に campaign / src / store を付ける
   ▼
[LP] 共通のテンプレート1つ … 開いた時にサーバーでセッションを作り、閲覧とタップを記録
   ▼
[予約の希望] フォームはセッション番号だけを持つ。施策はサーバーがセッションから決める
   ▼
[店の確定] 受付の画面で「確定（日時）」「受けられない」「取消」。日時の変更もここ
   ▼
[来店] 受付の画面の一覧から「来店」を押す。間違いは取り消せる
   ▼
[効果の画面] 漏斗と予約の内訳 ── 「分析を頼む」
   ▼
[分析エージェント] 検算 → 見立て → 追加の集計 → 見立てを直す → 報告
```

### 予約の約束

- お客様が送るのは **予約の希望**（希望日時つき）。完了画面には「希望を受け付けました。店から確定の連絡をします」と出す
- 店は電話で日時を決め、受付の画面で **確定日時** を入れる。日時が変わったら確定日時を直す
- 受けられない場合は「受けられない」、お客様の都合でやめる場合は「取消」

### 状態と移り変わり

| 状態 | 意味 | 次に移れる状態 |
|---|---|---|
| `requested` | 希望を受け付けた・店から未連絡 | `confirmed` / `declined` / `cancelled` |
| `confirmed` | 店が確定日時を入れた | `confirmed`（日時の変更） / `visited` / `cancelled` |
| `visited` | 来店を記録した | `confirmed`（来店の取り消し） |
| `declined` | 店が受けられなかった | なし |
| `cancelled` | お客様の都合でやめた | なし |

これ以外の移り変わりは保存の層で断る（例：取消の予約に来店を付けない）。

### 施策への割り当て

- LP を開くとサーバーがセッションを作る。セッションはそのタブの間だけ使い、**違う施策の URL を開いたら新しいセッション**にする
- 予約は、送ったフォームが持つセッションの `campaign`・`src`・`store` に割り当てる。1予約＝1施策
- 値が無い・台帳に無い施策は `unknown`（店ごとに `campaigns` に1行置き、参照が切れないようにする）。漏斗の外に「施策不明」として件数だけ出す
- フォームは開いた時に **送信キー** を持ち、同じキーで2回送られたら同じ予約番号を返す（2重の予約を作らない）

### 集計の対象

- 対象は **施策期間内に始まった LP のセッション**。そこから生まれた予約を、基準日時まで追いかける（月をまたいでも同じ集まりを追う）
- 段ごとに別の日付で切らない

### 漏斗（セッションの単位）

| 段 | 数え方 |
|---|---|
| LP を開いたセッション | 重複を除いて数える。「人数」とは呼ばない |
| 予約ボタンを押したセッション | 同じく重複を除く |
| 予約を送ったセッション | 1セッションから2台分の予約があっても1つ |

### 予約の内訳（予約の単位）

| 欄 | 数え方 |
|---|---|
| 予約の件数 | 対象のセッションから生まれた予約 |
| 未連絡・受けられない・取消 | それぞれの件数（来店率には入れない） |
| 来店 | 来店の記録がある確定予約（確定日との前後は問わない） |
| 来店待ち | 来店の記録が無く、確定日が「今日」以降 |
| 来店未記録 | 来店の記録が無く、確定日が「今日」より前。「来なかった」とは呼ばない |

- **来店率 ＝ 来店 ÷（来店 ＋ 来店未記録）**。分母が 0 なら「算出不可」
- 確定日が「今日」でまだ記録の無い予約は、その日が終わっていないので来店待ちに入れ、来店率には入れない。「来店」を押した時点で来店に移る
- 未連絡のまま来たお客様は、受付で「確定」→「来店」の2回押す（`requested` から直接 `visited` には移さない）
- **配った数（チラシの枚数・LINE の配信数）は参考の欄** に出し、分母にしない
- 画面と報告には必ず **施策期間と基準日時** を出す
- 画面の上に **「ネット予約で追えた分だけです。電話だけの予約・飛び込みの来店は入っていません」** と出す

## 4. 画面とエンドポイント

| 画面 | パス（案） | 誰が使う | 中身 |
|---|---|---|---|
| LP | `/lp/{store}?campaign=…&src=…` | お客様 | 共通のテンプレート1つ |
| 予約の希望 | `/reserve` | お客様 | メニュー・希望日時・名前・電話 |
| 受付の完了 | `/reserve/done/{reserve_no}` | お客様 | 予約番号と「店から確定の連絡をします」 |
| 受付 | `/desk` | 店の人 | ①未連絡の希望（確定・受けられない・取消・担当） ②今日の確定予約（来店ボタン） ③名前で検索 ④日付を選んで押し忘れた来店を記録 ⑤来店の取り消し |
| 効果の画面 | `/dashboard` | 店長 | 漏斗・予約の内訳・参考の欄・分析の依頼と結果 |

| API（案） | 何をする |
|---|---|
| `POST /api/sessions` | LP を開いた時にセッションを作る |
| `POST /api/events` | 閲覧・タップを記録 |
| `POST /api/reservations` | 予約の希望を保存（送信キーで2重を防ぐ） |
| `GET /api/reservations?status=…&date=…&q=…` | 受付の一覧と名前での検索 |
| `POST /api/reservations/{reserve_no}/confirm` ・ `/decline` ・ `/cancel` | 店の確定（日時の変更も confirm）・受けられない・取消 |
| `POST /api/visits` / `DELETE /api/visits/{reserve_no}` | 来店の記録とその取り消し |
| `GET /api/funnel` | 漏斗と予約の内訳（アプリの集計） |
| `POST /api/analysis` → `GET /api/analysis/{id}` | 分析の依頼と、結果・実行の記録の受け取り |

## 5. 台帳（SQLite）

| 表 | 列 | 制約・備考 |
|---|---|---|
| `stores` | `store_id`, `name` | 番号は固定の記号（例：`S-EKI`）。並び順で振らない |
| `campaigns` | `campaign`, `src`, `store_id`, `distributed`, `started_on`, `ended_on` | `(campaign, src, store_id)` で一意。店ごとに `unknown` の行を持つ。`distributed` は参考の欄にだけ使う |
| `sessions` | `session_id`, `started_at`, `campaign`, `src`, `store_id` | 施策は `campaigns` を参照 |
| `events` | `id`, `at`, `session_id`, `name` | `name` は `lp_view` と `reserve_tap` だけ |
| `reservations` | `reserve_no`, `submit_key`, `session_id`, `campaign`, `src`, `store_id`, `menu`, `requested_for`, `confirmed_for`, `status`, `handled_by`, `created_at`, `updated_at`, `customer_name`, `customer_phone` | `submit_key` は一意。施策はセッションから写す |
| `reservation_changes` | `id`, `reserve_no`, `at`, `from_status`, `to_status`, `confirmed_for`, `handled_by` | 状態と確定日時の変更の履歴（誰がいつ変えたか） |
| `visits` | `reserve_no`, `visited_at`, `recorded_at` | `reserve_no` で一意。`recorded_at` で押し忘れを後から記録したと分かる |
| `analysis_runs` | `analysis_id`, `as_of`, `status`, `export_csv`, `id_map_json`, `funnel_json`, `tool_log`, `report_json` | 分析ごとに、渡したもの・仮の番号の対応表・実行の記録を固定して残す。`id_map_json` は外に出さない |

決まり：

- 状態の変更・来店の記録・来店の取り消しは、履歴の追加と **一緒に成功するか、一緒に失敗する**（1つのトランザクション）
- 分析を頼んだ時、**1回の読み取り** から書き出しと集計を作り、`analysis_runs` に保存する。過去の時点を後から再現することはしない
- メニュー名は表を1つ決めて、その表記だけを使う

### 保存の層

台帳の読み書きはすべて `app/ledger.py` を通す。画面・エンドポイントには SQL を書かない。
状態の移り変わりの決まり（§3）もここで守る。
（ほかの業務アプリに置き換えやすくする狙いだが、今回は試していない）

## 6. 見本データ

- 生成するのは `scripts/make_sample.py`。**乱数の種を固定し、入力も決まった順に並べて**、誰が回しても同じ台帳になるようにする
- 範囲：駅前店 × チラシ・LINE × 2026年10月のセッション。予約・確定・来店は「今日」（§2）まで
- 数字の傾きは「よくありそう」な程度にとどめ、どこかの本物の店の実績を借りてこない
- 未連絡・受けられない・取消・日時の変更・来店待ち・来店未記録・押し忘れの後日記録・施策不明・2重送信も少し入れる（数え方の決まりが効いているかを見るため）
- **確定日が「今日」の予約** を数件入れる（受付の「今日の確定予約」が空にならず、デモで「来店」を押せるように）
- 人名・電話は一目で架空と分かる形（電話は `090-0000-` で始める）。車番は集めない

### 仕込み（1つ）

| 項目 | 中身 |
|---|---|
| 台帳から見つけられる事実 | 媒体別に見ると、チラシの来店率は LINE より低い。ところが「予約を送ってから確定日時までの日数」で分けると、同じ日数の中では差が小さくなる。チラシの予約は先の日に入りやすい |
| 台帳だけでは言い切れないこと | 先の日の予約で来店未記録が多い理由（お客様が忘れたのか、受付が押し忘れたのか、電話で別の日に来たのか、当日の天候で見送ったのか）。媒体が原因でないことも、日数が原因であることも断定できない |
| 期待する調べ方 | 最初の見立て「チラシが弱い」→ 日数で分けて集計 → 差が縮む → 見立てを「先の日の予約の扱い」に直す → 次の一手は「先の日の予約に前日の確認連絡をして、来店未記録が減るか見る」など |

- 生成スクリプトに **仕込みを切る指定** を付け、仕込みの無い台帳でもエージェントを回して、異常をでっち上げないかを確かめる
- 仕込みの中身は生成スクリプトと README で明かす

### 天候（初回は入れない・余裕があれば足す）

- 初回の台帳に天候は持たない。報告の「追加で確かめること」で、「日ごとの天候は台帳に無い。足せば確かめられる」と触れさせる
- 1店舗・1か月では雨の日が数日しかなく、天候の効果を見分けられる件数にならない。だから **天候に効果のある仕込みは入れない**
- 11/7 に一本通った後に余裕があれば、見本の `weather.csv`（`date`, `weather` = 晴・曇・雨、31行）を生成スクリプトで足す。**天候が来店に効かないように作り**、エージェントが「雨の日は来店が減る」とでっち上げないかの確認に使う
- 本物の天気（API・実在の地点）は使わない。外の仕組みに頼らず、見本の店の地域も特定させないため

## 7. 個人情報

- URL とログに入れてよいのは、店・施策・媒体・セッション番号・予約番号だけ
- 車番・LINE ID は集めない。名前と電話は、店がお客様に連絡し、受付で本人を確かめるためだけに持つ
- Claude に渡すのは、**書き出しの関数1つが許可した列だけ** と、アプリの集計値（列は §8「渡すもの」）。名前・電話・担当（`handled_by`）・送信キーは許可しない
- 予約番号とセッション番号は、書き出すたびに **仮の番号** に置き換える。対応表はアプリの中（`analysis_runs`）にだけ置き、外に出さない
- それでも日時などから台帳の予約と突き合わせられるので、「匿名化した」とは言わない。「指定した列だけの書き出し」と呼ぶ

## 8. 分析エージェント（Claude Managed Agents）

店長が漏斗を見て「分析を頼む」を押すと始まる。呼び出しは公式の Anthropic SDK（Python）。
モデルは `claude-opus-5-5` の予定。

**1回の呼び出しで文章を書かせる形との違い**：エージェントは集計を **コードで実行し**、その結果を見て次に切る軸を変える。
数字を文章の中で暗算させない。差は「追加の計算の結果で、見立てが変わった」ことで示す。

### 渡すもの

1. 許可した列だけの台帳の書き出し（表ごとに CSV を1つ）
2. アプリが計算した漏斗と予約の内訳（JSON）。施策期間・基準日（`as_of`）つき。1と同じ読み取りから作る

| CSV | 渡す列 | 何に使うか |
|---|---|---|
| `sessions.csv` | `session_id`※, `started_at`, `campaign`, `src`, `store_id` | 漏斗の検算（予約しなかったセッションも含む） |
| `events.csv` | `session_id`※, `at`, `name` | 予約ボタンを押したセッションの検算 |
| `reservations.csv` | `reserve_no`※, `session_id`※, `campaign`, `src`, `store_id`, `menu`, `requested_for`, `confirmed_for`, `status`, `created_at` | 予約の内訳の検算、予約から確定日までの日数（仕込み） |
| `visits.csv` | `reserve_no`※, `visited_at`, `recorded_at` | 来店の検算、押し忘れの後日記録 |
| `reservation_changes.csv` | `reserve_no`※, `at`, `from_status`, `to_status`, `confirmed_for` | 日時の変更と来店未記録の関係を確かめる |
| `campaigns.csv` | `campaign`, `src`, `store_id`, `distributed`, `started_on`, `ended_on` | 施策期間と、参考としての配った数 |

※ は仮の番号（例：`S0001`・`R001`）。セッションは開始日時の順、予約は作った日時の順に振り直し、表どうしのつながりは保つ。
渡さない列：`customer_name`・`customer_phone`・`handled_by`・`submit_key`・`updated_at`・実際の予約番号とセッション番号。

エージェントへの指示：配った数は参考の値で、漏斗の分母にしない。履歴から言えることも観測までにとどめ、原因は仮説として書く。

### 調べ方

1. **検算**：書き出しから漏斗と内訳をコードで数え直し、アプリの数字と比べる。合わなければ、分析より先に「食い違い」として報告する。一致しても「台帳が正しい」とは言わない（同じ入力に対する2つの集計が一致した、まで）
2. **見立てを置く**：段ごとの離脱数と離脱率、媒体ごとの来店率から、最初の見立てを1つ書く
3. **集計を重ねる**：見立てを確かめる軸（予約から確定日時までの日数・曜日・メニューなど）を選んで集計し直す。結果を見て、見立てを直すか次の軸を選ぶ
4. **報告**：「観測した事実」「原因の仮説」「追加で確かめること」を分けて書く。次の一手は **店全体で1つ**

### 実行の記録

- エージェントが回した集計（コード・結果・実行の番号）は、**アプリの側で** エージェントの実行の出来事から拾って `analysis_runs.tool_log` に残す。Claude が報告に書いた文章だけを記録として扱わない
- 報告の観測は、根拠にした実行の番号を持つ。画面では「何を集計し → 何が出て → どう見立てを変えたか」を短く並べる

### 報告の形（JSON・案）

```json
{
  "analysis_id": "",
  "as_of": "2026-11-07",
  "period": { "from": "2026-10-01", "to": "2026-10-31" },
  "reconciliation": { "matches": true, "differences": [] },
  "first_view": "",
  "revised_view": "",
  "observations": [{
    "statement": "",
    "scope": { "campaign": "", "src": "", "store_id": "" },
    "numerator": 0, "denominator": 0, "condition": "",
    "tool_run_ids": []
  }],
  "hypotheses": [{ "statement": "", "supporting": [], "how_to_check": "" }],
  "next_action": {
    "action": "", "effort": "", "metric": "",
    "comparison": "", "period": "", "provisional_target": ""
  }
}
```

- `first_view` → `revised_view`：最初の見立てと、追加の集計の後の見立て（変わらなければ同じでよい）
- `next_action` の目標値は試すための仮置き。超えても、それだけで「施策が効いた」とは言わない（比べる相手と期間を書く）

### 仕上がりの基準（outcomes に渡す）

- すべての観測に、分子・分母・集計の条件・根拠の実行の番号が付いている
- 検算がアプリの数字と一致している（または、食い違いを先に報告している）
- 観測・仮説・追加で確かめることが分かれている
- 許可していない列の値が出ていない

### 確かめ方

- 仕込みのある台帳と無い台帳の2つで回し、見立てと調べ方が変わるかを見る。無い台帳で「差が縮む」と言い出さないこと
- 見本の天候（§6）を足した後は、天候を渡しても「天候の効果」を観測として言わないこと（効果の無いように作ってあるため）。言うなら件数が足りないことを添えた仮説まで

### 11/3 に確かめること

- `claude-opus-5-5` と Managed Agents がこのアカウントで使えるか（使えるまでは決まったことにしない）
- コードを実行する道具の使い方、実行の出来事の拾い方、1回の分析の時間と使う量の上限、失敗した時の扱い
- 動かなければ、同じ入力・同じ報告の形で Messages API を1回呼ぶ形に **切り替える**。その場合は追加の集計ができないので、「同じ力」とは言わない

エージェントの定義（指示文・道具・基準）はファイルにして `agent/` に置き、変更を git で追えるようにする。

## 11. まだ決めていないこと

決める順番は **見つけたい事実（§6 の仕込みで決定）→ 正しい集計の条件（§3 で決定）→ 渡す表と列（§8 で決定）→ 見本データ → デモの日時**。

- メニューの一覧と施策コードの具体的な値
- 画面の文言（LP・予約の希望・受付・効果の画面）
- できれば、整備の店で働く人に聞く：今の突き合わせにかかる時間、電話での日程の変更、来店の記録を誰がするか、今の台帳への2重入力、受付で1件10秒の操作を足せるか。聞けなければ、現場の事実としては書かず仮説として残す

## 12. 言わないこと

- 「この施策が来店を生んだ」とは言わない。言えるのは「この施策経由の予約が来店した」まで
- 予算の配分（チラシを減らす・LINE に寄せる）を決められるとは言わない。費用・粗利・電話だけの予約を持っていない
- チラシ・LINE を「新しい集客」とは呼ばない（新しいお客様か分からない）。「店の外からの予約経路」と呼ぶ
- 来店の記録が無いことを「来なかった」とは言わない。「来店未記録」と呼ぶ
- 曜日や日数で差が出ても、それを原因とは言わない
- 検算が一致しても「台帳が正しい」とは言わない
- 「匿名化した」「業務アプリにそのまま移せる」とは言わない（試していない）
- 「店長の判断を変えた」は目標であって実績ではない。見本で仕込みが見つかっても、本物の店で効果が出た証拠とは言わない
