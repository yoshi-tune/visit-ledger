# 設計書（visit-ledger）

> 2026-11-02 版。Codex との1回目のディベート（審査員役・店長役）を受けて範囲を絞った。
> 出てくる店・数字・人はすべて見本。

## 1. 解きたい困りごと

舞台は **車の点検・整備を受け付ける地域の店**（オイル交換・タイヤ交換・点検など）。

見本の場面：月初、店長が先月のチラシと LINE 配信をふり返る。
チラシの枚数と LINE の配信数、ネット予約の件数は別々の画面や紙にあり、
「チラシ経由の予約のうち、何件が実際に来店したか」は手で突き合わせないと分からない。
だから「来月もチラシを刷るか、LINE に寄せるか」を勘で決めている。

visit-ledger は、施策の URL から来店までを **1本の台帳** に記録し、
「その施策経由の予約が、どれだけ来店まで進んだか」を施策ごとの漏斗で見せる。
最後に Claude の分析エージェントが台帳を **自分で集計し直しながら** 調べ、
抜けている段・考えられる理由・店として次に試す一手を、数字の根拠を付けて報告する。

役割の分け方：**アプリは数える。エージェントは調べて確かめる。店長が決める。**

### 作品の芯

> 施策付きの予約1件が来店までつながり、その台帳を Claude が追加で集計して、店長の判断を1つ変える。

これに効かないものは後回しにする。

## 3. 流れと数え方

```
[施策] チラシ・LINE・店頭 QR … URL に campaign / src / store を付ける
   ▼
[LP] 共通のテンプレート1つ … 開いた時にセッションを作り、閲覧とボタンのタップを記録
   ▼
[予約の希望] セッションごと施策を引き継いで保存 … 予約番号を発行
   ▼        （確定の連絡は店から電話。台帳の外）
[来店の受付] 今日の予約一覧から「来店」を押す、または予約番号を打つ
   ▼
[効果の画面] 施策ごとの漏斗 ── 「分析を頼む」
   ▼
[分析エージェント] 検算 → 集計を重ねて調べる → 報告
```

### 予約の約束

お客様が送るのは **予約の希望**。完了画面には「希望を受け付けました。店から確定の連絡をします」と出す。
空き枠の管理は作らない。

### 施策への割り当て（1つに固定）

- 予約は、送った時の **LP のセッション** に付いていた `campaign`・`src`・`store` に割り当てる。1予約＝1施策
- チラシも LINE も見た人でも、予約を送ったセッションの施策だけに付ける（ほかの施策には分けない）
- 値が無い・台帳に無い施策の場合は `campaign = unknown` で保存し、漏斗の外に「施策不明」として件数だけ出す

### 漏斗の段

| 段 | 数え方 |
|---|---|
| LP を開いたセッション | 施策ごとに `session_id` の重複を除いて数える。「人数」とは呼ばない |
| 予約ボタンを押したセッション | 同じく重複を除く。連打・再送は1つに数える |
| 予約の希望 | 予約の件数（取り消された予約は別に出す） |
| 来店 | 来店の記録がある予約の件数 |

- **配った数（チラシの枚数・LINE の配信数）は参考の欄**に出し、漏斗の分母にしない。媒体どうしで同じ物差しではないため
- **来店率の分母は「基準日時までに予約日を迎えた予約」**（取り消しを除く）。予約日がまだ来ていないものは「来店待ち」として別に出し、「来なかった」に入れない
- 画面と報告には必ず **集計期間と基準日時** を出す
- 店頭 QR（`src = store_qr`）は、すでに店にいる人が次回の予約をする経路。チラシ・LINE の新しい集客とは分けて並べる
- 画面の上に **「ネット予約で追えた分だけです。電話・飛び込みの来店は入っていません」** と出す

## 4. 画面とエンドポイント

| 画面 | パス（案） | 誰が使う | 中身 |
|---|---|---|---|
| LP | `/lp/{store}?campaign=…&src=…` | お客様 | 共通のテンプレート1つ |
| 予約の希望 | `/reserve` | お客様 | 最小の入力（メニュー・希望日時・名前・電話）。施策はセッションから引き継ぐ |
| 受付の完了 | `/reserve/done/{reserve_no}` | お客様 | 予約番号を大きく出す |
| 来店の受付 | `/visit` | 店の人 | 今日の予約一覧に「来店」ボタン。番号の入力欄。間違えた来店の取り消し |
| 効果の画面 | `/dashboard` | 店長 | 漏斗・参考の欄・分析の依頼と結果 |

作らないもの：カメラでの QR 読み取り、お客様が自分で予約を見直す・取り消す画面、店ごとの LP の作り込み、設定画面。

| API（案） | 何をする |
|---|---|
| `POST /api/sessions` | LP を開いた時にセッションを作る |
| `POST /api/events` | 閲覧・タップを記録 |
| `POST /api/reservations` | 予約の希望を保存 |
| `GET /api/reservations?date=today&store=…` | 来店の受付用の一覧 |
| `POST /api/visits` / `DELETE /api/visits/{reserve_no}` | 来店の記録と、その取り消し |
| `GET /api/funnel` | 施策ごとの漏斗（アプリの集計） |
| `POST /api/analysis` → `GET /api/analysis/{id}` | 分析の依頼と、結果・途中経過の受け取り |

## 5. 台帳（SQLite）

| 表 | 列 | 制約・備考 |
|---|---|---|
| `stores` | `store_id`, `name` | 番号は固定の記号（例：`S-EKI`）。並び順で振らない |
| `campaigns` | `campaign`, `src`, `store_id`, `distributed`, `started_on`, `ended_on` | `(campaign, src, store_id)` で一意。`distributed` は参考の欄にだけ使う |
| `sessions` | `session_id`, `started_at`, `campaign`, `src`, `store_id` | 施策は `campaigns` を参照（不明は `unknown`） |
| `events` | `id`, `at`, `session_id`, `name` | `name` は `lp_view` と `reserve_tap` だけ |
| `reservations` | `reserve_no`, `session_id`, `campaign`, `src`, `store_id`, `menu`, `reserved_for`, `created_at`, `status`, `customer_name`, `customer_phone` | 施策は `session_id` から写す。`status` は `requested` / `visited` / `cancelled` |
| `visits` | `reserve_no`, `visited_at` | `reserve_no` で一意（1予約に1来店）。店は予約から取る |

決まり：

- 来店の記録と予約の `status` の更新は、**一緒に成功するか、一緒に失敗する**（1つのトランザクション）
- 同じ予約に2回目の来店は付けない。台帳に無い予約番号は受け付けない。取り消すと `status` は `requested` に戻る
- メニュー名は表を1つ決めて、その表記だけを使う
- 分析を頼んだ時に **基準日時（`as_of`）を1つ決め**、アプリの集計と書き出しは同じ時点の台帳から作る

### 保存の層

台帳の読み書きはすべて `app/ledger.py` を通す。画面・エンドポイントには SQL を書かない。
（ほかの業務アプリに置き換えやすくする狙いだが、今回は試していない）

## 6. 見本データ

- 生成するのは `scripts/make_sample.py`。**乱数の種を固定し、入力も決まった順に並べて**、誰が回しても同じ台帳になるようにする
- 規模：見本の店は3つ（駅前店・バイパス店・郊外店）× 媒体3種（チラシ・LINE 配信・店頭 QR）× 1か月
- 数字の傾きは「よくありそう」な程度にとどめ、どこかの本物の店の実績を借りてこない
- 予約日がまだ来ていない予約・取り消し・施策不明の予約も少し入れる（数え方の決まりが効いているかを見るため）
- **仕込み** は1〜2個。1つごとに「台帳から見つけられる事実」と「台帳だけでは言い切れない理由」をセットで決め、生成スクリプトと README で明かす
- 仕込みの無い所でエージェントが異常をでっち上げないかも確かめる
- 人名・電話は一目で架空と分かる形（電話は `090-0000-` で始める）。車番は集めない

## 7. 個人情報

- URL とログに入れてよいのは、店・施策・媒体・セッション番号・予約番号だけ
- 車番・LINE ID は集めない。名前と電話は来店の受付で本人を確かめるためだけに持つ
- Claude に渡すのは、**書き出しの関数1つが許可した列だけ**（許可した列だけを出す方式）と、アプリの集計値。名前・電話は許可しない
- 予約番号などの識別子は残るので、「匿名化した」とは言わない。「指定した列だけの書き出し」と呼ぶ

## 8. 分析エージェント（Claude Managed Agents）

店長が漏斗を見て「分析を頼む」を押すと始まる。呼び出しは公式の Anthropic SDK（Python）。
モデルは `claude-opus-5-5` の予定。

**Messages API を1回呼んで答えさせる形との違い**：エージェントは集計を **コードで実行し**、その結果を見て次に切る軸を変える。
数字を文章の中で暗算させない。どの集計を、どの順で回し、何が出たかを画面に記録として出す。

### 渡すもの

1. 許可した列だけの台帳の書き出し（CSV）。基準日時つき
2. アプリが計算した漏斗の数字（JSON）。同じ基準日時

### 調べ方

1. **検算**：書き出しから漏斗をコードで数え直し、アプリの数字と比べる。合わなければ、分析より先に「台帳の食い違い」として報告する
2. **抜けている段を見る**：施策ごとに、段ごとの **離脱数と離脱率の両方** を出す。数が一番多い段と率が一番高い段は別のことがある
3. **集計を重ねる**：最初の見立てを置き、店・曜日・媒体・予約から予約日までの日数などで集計し直す。結果を見て、見立てを直すか次の軸を選ぶ
   - 例：来店率が低い → 予約日までの日数で分ける → 来店待ちが多く混ざっていた → 分母を直して検算し直す
4. **報告**：「観測した事実」「原因の仮説」「追加で確かめること」を分けて書く。次の一手は **店全体で1つ**

### 報告の形（JSON・案）

```json
{
  "as_of": "2026-11-30T23:59:00+09:00",
  "period": { "from": "2026-11-01", "to": "2026-11-30" },
  "reconciliation": { "matches": true, "differences": [] },
  "trace": [{ "step": 1, "query": "", "result_summary": "", "decision": "" }],
  "observations": [{
    "statement": "",
    "scope": { "campaign": "", "src": "", "store_id": "" },
    "numerator": 0, "denominator": 0, "condition": ""
  }],
  "hypotheses": [{ "statement": "", "supporting": [], "how_to_check": "" }],
  "next_action": {
    "action": "", "effort": "", "metric": "",
    "comparison": "", "period": "", "provisional_target": ""
  }
}
```

- `trace`：エージェントが回した集計の記録。画面では「何を調べ → 何が出て → どう決めたか」を短く並べる
- `observations`：台帳の数字で言えること。分子・分母・集計の条件を必ず持つ
- `hypotheses`：言い切らない。何を集めれば確かめられるかを添える
- `next_action`：目標値は試すための仮置き。目標を超えても、それだけで「施策が効いた」とは言わない（比べる相手と期間を書く）

### 仕上がりの基準（outcomes に渡す）

- すべての観測に分子・分母・集計の条件が付いている
- 検算がアプリの数字と一致している（または、食い違いを先に報告している）
- 観測・仮説・追加で確かめることが分かれている
- 許可していない列の値が出ていない

### 11/3 に確かめること

- `claude-opus-5-5` と Managed Agents がこのアカウントで使えるか（使えるまでは決まったことにしない）
- コードを実行する道具の使い方、1回の分析にかかる時間と使う量の上限、失敗した時の扱い
- ここで動かなければ、同じ入力・同じ報告の形で Messages API を1回呼ぶ形に **切り替える**（両方は作り込まない）

エージェントの定義（指示文・道具・基準）はファイルにして `agent/` に置き、変更を git で追えるようにする。

## 9. 構成

| 項目 | 選んだもの |

```
visit-ledger/
├─ app/

│  ├─ analysis/        … エージェントの呼び出し（動かなければ予備）

├─ scripts/make_sample.py
├─ docs/DESIGN.md
├─ README.md
└─ BUILD_LOG.md
```

## 12. 言わないこと

- 「この施策が来店を生んだ」とは言わない。言えるのは「この施策経由の予約が来店した」まで
- 曜日や店で差が出ても、それを原因とは言わない
- 「匿名化した」「業務アプリにそのまま移せる」とは言わない（試していない）
- 見本データで仕込みが見つかっても、本物の店で効果が出た証拠とは言わない
