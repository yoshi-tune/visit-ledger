# 設計書（visit-ledger）

> 2026-11-02 版（下書き）。この後、批判役とのディベートで範囲を詰めて直す。
> 出てくる店・数字・人はすべて見本。

## 1. 解きたい困りごと

地域のお店は、チラシを配り、LINE で配信し、店ごとの Web ページ（LP）を用意している。
ところが「その施策を見た人が予約し、本当に来店したか」は別々の場所に散らばっていて、
**施策ごとに最後まで追えない**。分かるのは「何枚配った」「何回開かれた」までで、
どの施策が来店を生んだのか、どこで人が抜けたのかは勘で語られている。

visit-ledger は、施策の始まりから来店までを **1本の台帳** に記録し、
施策ごとの「漏斗」（各段で何人残ったか）として見せる。
最後に Claude の分析エージェントが台帳を自分で調べ、
「どこで抜けているか・なぜか・次に何を試すか」を、数字の根拠を付けて報告する。

役割の分け方：**アプリは数える。エージェントは調べて確かめる。人は決める。**

## 3. 流れと4つのつなぎ目

```
[施策] チラシ・LINE・店頭 QR
   │  URL に campaign / src / store を付けて配る
   ▼
[LP] 店のページ ── 閲覧・予約ボタンのタップを記録
   │  ① 同じ 3 つの値を予約フォームに引き継ぐ
   ▼
[予約] 予約番号（reserve_no）を発行して記録
   │  ② 来店時に予約番号の QR を読む（またはコード入力）
   ▼
[来店] 予約の状態を「来店」にする
   │  ③ 予約番号から施策までさかのぼる
   ▼
[効果の画面] ④ 施策ごとの漏斗 ── 「分析を頼む」
   ▼
[分析エージェント] 検算 → どこで抜けたか → なぜか → 次の一手
```

| # | つなぎ目 | 決まり |
|:-:|---|---|
| ① | LP → 予約 | 予約ボタンのリンクに `campaign`・`src`・`store` をそのまま載せる。予約1件にこの3つを必ず保存する |
| ② | 予約 → 来店 | 来店の記録は `reserve_no` だけで作る。予約の無い飛び込みは今回は扱わない |
| ③ | 来店 → 施策 | 来店 → 予約 → `campaign`+`src`+`store` とたどる。別のつなぎ方は作らない |
| ④ | 漏斗 | 段は「配った数 → LP を見た人 → 予約ボタンを押した人 → 予約 → 来店」。各段の数と、前の段から抜けた割合を出す |

## 4. 画面とエンドポイント

| 画面 | パス（案） | 誰が使う |
|---|---|---|
| LP | `/lp/{store}?campaign=…&src=…` | お客様（チラシの QR・LINE のリンクから来る） |
| 予約フォーム | `/reserve?campaign=…&src=…&store=…` | お客様 |
| 予約の完了 | `/reserve/done/{reserve_no}` | お客様（来店時に見せる QR を出す） |
| 来店の読み取り | `/visit` | 店の人（QR を読む・番号を打つ） |
| 効果の画面 | `/dashboard` | 店長・本部 |

| API（案） | 何をする |
|---|---|
| `POST /api/events` | LP の閲覧・タップを記録 |
| `POST /api/reservations` | 予約を作る |
| `POST /api/visits` | 来店を記録する |
| `GET /api/funnel` | 施策ごとの漏斗（アプリの集計） |
| `POST /api/analysis` → `GET /api/analysis/{id}` | 分析の依頼と結果の受け取りを分ける（時間がかかるため） |

## 5. 台帳（SQLite）

| 表 | 列 | 備考 |
|---|---|---|
| `stores` | `store_id`, `name` | 番号は並び順ではなく固定の記号で振る（例：`S-EKI`） |
| `campaigns` | `campaign`, `src`, `store_id`, `distributed`, `started_on` | `distributed` は配信数・配布数。施策コードは `{メニュー}_{YYYYMM}` |
| `events` | `id`, `at`, `session_id`, `campaign`, `src`, `store_id`, `name` | `name` は `lp_view` と `reserve_tap` の2種類だけ |
| `reservations` | `reserve_no`, `confirm_key`, `store_id`, `menu`, `reserved_for`, `created_at`, `status`, `campaign`, `src`, `channel`, `customer_name`, `customer_phone` | 名前と電話は**個人情報の列**。外に出すときは必ず外す |
| `visits` | `reserve_no`, `visited_at`, `store_id` | 1予約に1来店 |

決まり：

- 予約と来店をつなぐのは `reserve_no`、施策までさかのぼるのは `campaign`+`src`+`store_id`
- タップは1種類のイベントだけで数える（2回数えない）
- メニュー名は表を1つ決めて、その表記だけを使う
- `status` は `reserved` / `visited` / `cancelled`

### 保存の層

台帳の読み書きはすべて `app/ledger.py` を通す。画面・エンドポイントには SQL を書かない。
後で業務アプリ（例：kintone）に差し替えるとしても、ここだけ取り替えれば済む形にしておく。

## 6. 見本データ

- 生成するのは `scripts/make_sample.py`。**乱数の種を固定し、入力も決まった順に並べて**、誰が回しても同じ台帳になるようにする
- 規模：見本の店は3つ（駅前店・バイパス店・郊外店）× 媒体3種（チラシ・LINE 配信・店頭 QR）× 1か月
- 数字の傾きは「よくありそう」な程度にとどめ、どこかの本物の店の実績を借りてこない
- エージェントに見つけさせる **仕込み** を1〜2個入れ、生成スクリプトと README で中身を明かす
- 人名・電話は一目で架空と分かる形（電話は `090-0000-` で始める）

## 7. 個人情報

- URL とログに入れてよいのは、店・施策・媒体・予約番号だけ
- お客様が予約を見直したり取り消したりするときは、予約番号に加えて確認キーを求める（番号だけでは開けない）
- Claude に渡すのは、**個人情報の列を落とした台帳の書き出し** と **アプリの集計値** だけ。書き出す関数を1つにして、そこで列を落とす
- 落とす列：`customer_name`・`customer_phone`（個人情報）、`confirm_key`（予約ごとの合言葉）

## 8. 分析エージェント（Claude Managed Agents）

店長が漏斗を見て「分析を頼む」を押すと始まる。モデルは `claude-opus-5-5`、呼び出しは公式の Anthropic SDK（Python）。

### 渡すもの

1. 個人情報の列を落とした台帳の書き出し（CSV）
2. アプリが計算した漏斗の数字（JSON）

### させること（4段）

| 段 | 中身 | 守らせること |
|---|---|---|
| 検算 | 台帳から漏斗を数え直し、アプリの数字と比べる | 合わなければ、分析より先に「台帳の食い違い」として報告する |
| どこで | 施策ごとに、一番人が抜けている段を示す | 段の数・抜けた割合・その計算式を添える |
| なぜ | 理由の仮説を立て、店・曜日・媒体・予約から来店までの日数などで切って確かめる | 「確かめられた」と「まだ確かめられない（何を集めれば分かるか）」を分ける。言い切らない |
| 次の一手 | 1つの施策につき、試すことを1〜2個 | 「効いた」と判断する指標と、その目標値をセットで書く |

### 報告の形（JSON・案）

```json
{
  "reconciliation": { "matches": true, "differences": [] },
  "bottlenecks": [{ "campaign": "", "stage": "", "rate": 0, "formula": "" }],
  "hypotheses": [{
    "claim": "",
    "status": "confirmed | needs_data",
    "evidence": [{ "figure": "", "formula": "" }],
    "data_needed": ""
  }],
  "next_actions": [{ "campaign": "", "action": "", "metric": "", "target": "" }]
}
```

画面では、各文の横に根拠の数字と式を並べる。

### 仕上がりの基準（outcomes に渡す）

- すべての主張に、台帳の数字と計算式が付いている
- 検算の結果がアプリの数字と一致している（または、食い違いを先に報告している）
- 「確かめられた」と「まだ確かめられない」が分かれている
- 個人情報が出ていない

### 予備

エージェントが動かない場合に備えて、同じ入力・同じ報告の形のまま Messages API を1回呼ぶ形も作る。
1回の分析ごとに使う量の上限を決める。

エージェントの定義（指示文・道具・基準）はファイルにして `agent/` に置き、変更を git で追えるようにする。
細かい呼び方は 11/3 のワークショップの後に決める。

## 9. 構成

| 項目 | 選んだもの |
|---|---|
| サーバー | Python・FastAPI、依存は uv（`uv add` / `uv run`） |
| 台帳 | SQLite（DB のファイルはリポジトリに入れない。見本は生成スクリプトから作る） |
| 画面 | 素の HTML と JS。JS の先頭に `// @ts-check`。ビルドとフレームワークは入れない |
| 鍵 | `ANTHROPIC_API_KEY` は環境変数から読む。`.env` は git に入れない |

```
visit-ledger/
├─ app/
│  ├─ main.py          … FastAPI の入口・ルーティング
│  ├─ ledger.py        … 保存の層（SQL はここだけ）
│  ├─ funnel.py        … 漏斗の集計
│  ├─ export.py        … 個人情報を落とした書き出し
│  ├─ analysis/        … エージェントの呼び出しと予備
│  └─ static/          … HTML・JS・CSS
├─ agent/              … エージェントの定義
├─ scripts/make_sample.py
├─ docs/DESIGN.md
├─ README.md
└─ BUILD_LOG.md
```
