## 1. 解きたい困りごと

舞台は **車の点検・整備を受け付ける地域の店**（オイル交換・タイヤ交換・点検など）。

見本の場面：月初、店長が先月のチラシと LINE 配信をふり返る。
チラシの枚数・LINE の配信数・ネット予約・来店は、別々の画面や紙にある。
「チラシ経由の予約のうち、何件が実際に来店したか」は手で突き合わせないと分からず、
「チラシは効いていないのでは」という印象だけが残る。

visit-ledger は、施策の URL から予約・来店までを **1本の台帳** に記録し、
「その施策経由の予約が、どこまで進んだか」を施策ごとに見せる。
最後に Claude の分析エージェントが台帳を **自分で集計し直しながら** 調べ、
最初の見立てが追加の集計でどう変わったかと、店として次に確かめる一手を、数字の根拠を付けて報告する。

役割の分け方：**アプリは数える。エージェントは調べて確かめる。店長が決める。**

### 作品の芯

> 施策付きの予約1件が、店での確定を経て来店までつながる。その台帳を Claude が追加で集計し、
> 店長が「次に何を確かめるか」を1つ決められる。

これに効かないものは後回しにする。予算の配分（チラシをやめるか等）を決める道具ではない（§12）。

## 3. 流れと数え方

```
[施策] チラシ・LINE … URL に campaign / src / store を付ける
   ▼
[LP] 共通のテンプレート1つ … 開いた時にサーバーでセッションを作り、閲覧とタップを記録
   ▼
[予約] 空いている日時だけを選べる。送った時点で確定。施策はサーバーがセッションから決める
   ▼
[来店] 受付の画面の一覧から「来店」を押す。間違いは取り消せる。日時の変更・取消も受付で
   ▼
[効果の画面] 来店までの道のりと予約の内訳 ── 「分析を頼む」
   ▼
[分析エージェント] 検算 → 見立て → 追加の集計 → 見立てを直す → 報告
```

### 予約の約束（11/2 夜に切り替え）

- **お客様が送った時点で予約が確定する**。店から電話で確定する作業は無い（知らない番号の電話に出ない人が多く、電話での確定は今の利用者に合わないため）
- 選べるのは **空いている日時だけ**。空きは店のマスタ（時間帯ごとの台数・休みの曜日・休みの日）と台帳の予約から、サーバーが数える。満席の枠や休みの日には、サーバーの側でも予約を入れない（2人が同時に最後の1枠を取らないよう、確かめと書き込みを1つのトランザクションで行う）
- お客様の都合で日時を変える・やめる時は、お客様が店に連絡し、店が受付で「日時を変える」「取消」を行う（取消は枠を空ける）
- 店のマスタは、スタッフ側の「店の設定」の画面で変える。変えても、すでに入っている予約は動かさない

### 状態と移り変わり

| 状態 | 意味 | 次に移れる状態 |
|---|---|---|
| `confirmed` | 予約が確定している | `confirmed`（日時の変更） / `visited` / `cancelled` |
| `visited` | 来店を記録した | `confirmed`（来店の取り消し） |
| `cancelled` | お客様の都合でやめた | なし |

これ以外の移り変わりは保存の層で断る（例：取消の予約に来店を付けない・来店済みの日時を変えない）。

### 施策への割り当て

- LP を開くとサーバーがセッションを作る。セッションはそのタブの間だけ使い、**違う施策の URL を開いたら新しいセッション**にする
- 予約は、送ったフォームが持つセッションの `campaign`・`src`・`store` に割り当てる。1予約＝1施策
- 値が無い・台帳に無い施策は `unknown`（店ごとに `campaigns` に1行置き、参照が切れないようにする）。来店までの道のりの外に「施策不明」として件数だけ出す
- フォームは開いた時に **送信キー** を持ち、同じキーで2回送られたら同じ予約番号を返す（2重の予約を作らない）

### 集計の対象

- 対象は **施策期間のうち「今日」までに始まった LP のセッション**。そこから生まれた予約を、基準日まで追いかける（月をまたいでも同じ集まりを追う）
- 段ごとに別の日付で切らない

### 来店までの道のり（セッションの単位）

| 段 | 数え方 |
|---|---|
| LP を開いたセッション | 重複を除いて数える。「人数」とは呼ばない |
| 予約ボタンを押したセッション | 同じく重複を除く |
| 予約を送ったセッション | 1セッションから2台分の予約があっても1つ |

### 予約の内訳（予約の単位）

| 欄 | 数え方 |
|---|---|
| 予約の件数 | 対象のセッションから生まれた予約 |
| 取消 | 件数（来店率には入れない） |
| 来店 | 来店の記録がある予約（来店予定日との前後は問わない） |
| 来店待ち | 来店の記録が無く、来店予定日（`confirmed_for`）が「今日」以降 |
| 来店未記録 | 来店の記録が無く、来店予定日が「今日」より前。「来なかった」とは呼ばない |

- **来店率 ＝ 来店 ÷（来店 ＋ 来店未記録）**。分母が 0 なら「算出不可」
- 来店予定日が「今日」でまだ記録の無い予約は、その日が終わっていないので来店待ちに入れ、来店率には入れない。「来店」を押した時点で来店に移る
- **配った数（チラシの枚数・LINE の配信数）は参考の欄** に出し、分母にしない
- 画面と報告には必ず **施策期間と基準日時** を出す
- 画面の上に **「ネット予約で追えた分だけです。電話だけの予約・飛び込みの来店は入っていません」** と出す

### クーポン（11/2 夜に追加）

LP の「クーポン」（見本：点検 ¥500 引き）で、そのセッションにクーポンを1つ出す（もう一度押しても同じ番号）。お客様は QR と番号を受付で見せ、受付は QR を店のスマホで読むか番号を入れて、**「使った」を押した時だけ**記録する（開いただけでは記録しない・1つの番号で1回だけ）。クーポンを出したセッションに予約があれば、その予約と結ぶ。無ければ **予約なしの来店** として残る。

| 欄 | 数え方 |
|---|---|
| LP で出した | クーポンを出したセッションの数 |
| 店で使った | そのうち店で使った数。うち予約あり（セッションに予約がある）／うち予約なし |

- 来店率の数え方は変えない（クーポンの欄は別に出す）。「予約なし」は、そのセッションに予約が無いという意味で、電話など別の道で予約した人も入りうる
- QR の中身は受付の画面の URL（`/desk/coupon/{番号}`）だけ。番号は無作為で、何も表さない。書き出しでは番号を落とす
- 今の現場では LP のクーポンのボタンを押した数までしか分からず、店で使ったかは残っていない（作品の出発点の1つ）

## 5. 台帳（SQLite）

| `stores` | `store_id`, `name` | 番号は固定の記号（例：`S-EKI`）。並び順で振らない |
| `campaigns` | `campaign`, `src`, `store_id`, `distributed`, `started_on`, `ended_on` | `(campaign, src, store_id)` で一意。店ごとに `unknown` の行を持つ。`distributed` は参考の欄にだけ使う |
| `sessions` | `session_id`, `started_at`, `campaign`, `src`, `store_id` | 施策は `campaigns` を参照 |
| `events` | `id`, `at`, `session_id`, `name` | `name` は `lp_view` と `reserve_tap` だけ |
| `reservations` | `reserve_no`, `submit_key`, `session_id`, `campaign`, `src`, `store_id`, `menu`, `requested_for`, `confirmed_for`, `status`, `handled_by`, `created_at`, `updated_at`, `customer_name`, `customer_phone` | `submit_key` は一意。施策はセッションから写す。`requested_for` は最初に予約した日時、`confirmed_for` は今の来店予定日時（日時を変えると変わる） |

| `closed_weekdays` / `closed_dates` | `store_id`, `weekday` ／ `store_id`, `day`, `note` | 店のマスタ：休みの曜日（0=月…6=日）と休みの日 |
| `reservation_changes` | `id`, `reserve_no`, `at`, `from_status`, `to_status`, `confirmed_for`, `handled_by` | 状態と確定日時の変更の履歴（誰がいつ変えたか） |

| `analysis_messages` | `id`, `analysis_id`, `at`, `role`, `status`, `text`, `tool_log` | 分析の続きの質問と答え |
| `improvements` | `id`, `created_at`, `iteration`, `status`, `decision`, `reason`, `base_system`, `candidate_system`, `proposal_json`, `eval_base_json`, `eval_cand_json`, `applied_at` | 分析担当の見直し：直しの案・物差しの結果・残したか戻したか・本番に使ったか |
| `settings_versions` | `version`, `created_at`, `settings_json`, `change_request_id`, `note` | 受付に足したタブの設定の版（取り消しは、前の版の中身で新しい版を作る） |
| `change_requests` | `id`, `created_at`, `requested_by`, `text`, `source_analysis_id`, `proposal_json`, `status`, `reason`, `applied_version`, `applied_by`, `applied_at` | ナットクに頼んだ記録（提案・反映・やめた・取り消した・捨てた） |
| `reminders` | `id`, `reserve_no`, `at`, `result`, `handled_by`, `desk_tab_id` | 前日のお知らせの記録（`sent`・`replied`・`rescheduled`）。タブを外しても消さない |

決まり：

- 状態の変更・来店の記録・来店の取り消しは、履歴の追加と **一緒に成功するか、一緒に失敗する**（1つのトランザクション）
- 分析を頼んだ時、**1回の読み取り** から書き出しと集計を作り、`analysis_runs` に保存する。過去の時点を後から再現することはしない
- メニュー名は表を1つ決めて、その表記だけを使う

### 保存の層

台帳の読み書きはすべて `app/ledger.py` を通す。画面・エンドポイントには SQL を書かない。
状態の移り変わりの決まり（§3）もここで守る。
（ほかの業務アプリに置き換えやすくする狙いだが、今回は試していない）

## 6. 見本データ

- 生成するのは `scripts/make_sample.py`。**乱数の種を固定し、入力も決まった順に並べて**、誰が回しても同じ台帳になるようにする
- 範囲：駅前店 × チラシ・LINE × 2026年10月のセッション。予約・確定・来店は「今日」（§2）まで
- 施策は `autumn_check_202610`（秋の点検）の1つを、チラシ（3000枚）と LINE（1200通）で配る。メニューは「オイル交換・タイヤ交換・秋の点検」で、**どちらの媒体でも同じ割合**（比べる軸を媒体だけにして、見立てが変わる場面を1本にするため）
- 規模：LP のセッションはチラシ 250・LINE 600、予約はチラシ 50・LINE 70
- 来店の結果はさいころで決めず、媒体 × 日数のマスごとに件数の割合で割り当てる（種によって仕込みが消えないように）
- 数字の傾きは「よくありそう」な程度にとどめ、どこかの本物の店の実績を借りてこない
- 取消・日時の変更・来店待ち・来店未記録・押し忘れの後日記録・施策不明・2重送信も少し入れる（数え方の決まりが効いているかを見るため）
- 店のマスタは、10・11・13・14・15・16時に各2台・毎週水曜は休み。見本の予約もこのマスタを守る（満席の枠・水曜には入れない）
- **確定日が「今日」の予約** を数件入れる（受付の「今日の確定予約」が空にならず、デモで「来店」を押せるように）
- 人名・電話は一目で架空と分かる形（電話は `090-0000-` で始める）。車番は集めない

### 仕込み（1つ）

| 項目 | 中身 |
|---|---|
| 台帳から見つけられる事実 | 媒体別に見ると、チラシの来店率は LINE より低い。ところが「予約を送ってから確定日時までの日数」で分けると、同じ日数の中では差が小さくなる。チラシの予約は先の日に入りやすい |
| 台帳だけでは言い切れないこと | 先の日の予約で来店未記録が多い理由（お客様が忘れたのか、受付が押し忘れたのか、連絡なく別の日に来たのか、当日の天候で見送ったのか）。媒体が原因でないことも、日数が原因であることも断定できない |
| 期待する調べ方 | 最初の見立て「チラシが弱い」→ 日数で分けて集計 → 差が縮む → 見立てを「先の日の予約の扱い」に直す → 次の一手は「先の日の予約に前日の確認連絡をして、来店未記録が減るか見る」など |

- 生成スクリプトに **仕込みを切る指定** を付け、仕込みの無い台帳でもエージェントを回して、異常をでっち上げないかを確かめる
- 仕込みの中身は生成スクリプトと README で明かす
- クーポンは仕込みを入れない：LP を開いたセッションの 30% が出し、予約して来店した人の 60%・予約しなかった人の 8% が使う（どちらの媒体でも同じ割合）。乱数は別の種で、予約まで作った後に足す（前からの数字を動かさない）

### 天候（初回は入れない・余裕があれば足す）

- 初回の台帳に天候は持たない。報告の「追加で確かめること」で、「日ごとの天候は台帳に無い。足せば確かめられる」と触れさせる
- 1店舗・1か月では雨の日が数日しかなく、天候の効果を見分けられる件数にならない。だから **天候に効果のある仕込みは入れない**
- 11/7 に一本通った後に余裕があれば、見本の `weather.csv`（`date`, `weather` = 晴・曇・雨、31行）を生成スクリプトで足す。**天候が来店に効かないように作り**、エージェントが「雨の日は来店が減る」とでっち上げないかの確認に使う
- 本物の天気（API・実在の地点）は使わない。外の仕組みに頼らず、見本の店の地域も特定させないため

## 7. 個人情報

- URL とログに入れてよいのは、店・施策・媒体・セッション番号・予約番号だけ
- 車番・LINE ID は集めない。名前と電話は、店から連絡が必要な時と、受付で本人を確かめるためだけに持つ
- Claude に渡すのは、**書き出しの関数1つが許可した列だけ** と、アプリの集計値（列は §8「渡すもの」）。名前・電話・担当（`handled_by`）・送信キーは許可しない
- 予約番号とセッション番号は、書き出すたびに **仮の番号** に置き換える。対応表はアプリの中（`analysis_runs`）にだけ置き、外に出さない
- それでも日時などから台帳の予約と突き合わせられるので、「匿名化した」とは言わない。「指定した列だけの書き出し」と呼ぶ

## 8. 分析エージェント（Claude Managed Agents）

店長が来店までの道のりを見て「分析を頼む」を押すと始まる。呼び出しは公式の Anthropic SDK（Python）。
モデルは既定 `claude-opus-5-5`。効果の画面で Sonnet 5.5・Haiku 5.5 も選べる（セッションだけモデルを差し替える。エージェントの版は変えない）。
報告の後は、同じセッション（台帳の CSV と集計のスクリプトが残っている）に店長の質問を送る。エージェントは `chat_NN.py` を書いて数え直して答える。1回の分析の上限（既定 $3）は続きの質問も含む。

**1回の呼び出しで文章を書かせる形との違い**：エージェントは集計を **コードで実行し**、その結果を見て次に切る軸を変える。
数字を文章の中で暗算させない。差は「追加の計算の結果で、見立てが変わった」ことで示す。

### 渡すもの

1. 許可した列だけの台帳の書き出し（表ごとに CSV を1つ）
2. アプリが計算した来店までの道のりと予約の内訳（JSON）。施策期間・基準日（`as_of`）つき。1と同じ読み取りから作る

| CSV | 渡す列 | 何に使うか |
|---|---|---|
| `sessions.csv` | `session_id`※, `started_at`, `campaign`, `src`, `store_id` | 来店までの道のりの検算（予約しなかったセッションも含む） |
| `events.csv` | `session_id`※, `at`, `name` | 予約ボタンを押したセッションの検算 |
| `reservations.csv` | `reserve_no`※, `session_id`※, `campaign`, `src`, `store_id`, `menu`, `requested_for`, `confirmed_for`, `status`, `created_at` | 予約の内訳の検算、予約した日から来店予定日までの日数（仕込み） |
| `visits.csv` | `reserve_no`※, `visited_at`, `recorded_at` | 来店の検算、押し忘れの後日記録 |
| `reservation_changes.csv` | `reserve_no`※, `at`, `from_status`, `to_status`, `confirmed_for` | 日時の変更と来店未記録の関係を確かめる |
| `campaigns.csv` | `campaign`, `src`, `store_id`, `distributed`, `started_on`, `ended_on` | 施策期間と、参考としての配った数 |
| `coupons.csv` | `session_id`※, `issued_at`, `redeemed_at`, `reserve_no`※ | クーポンを出した・使った・結んだ予約（空なら予約なしの来店）。番号は渡さない |

※ は仮の番号（例：`S0001`・`R001`）。セッションは開始日時の順、予約は作った日時の順に振り直し、表どうしのつながりは保つ。
渡さない列：`customer_name`・`customer_phone`・`handled_by`・`submit_key`・`updated_at`・クーポンの番号（`code`）・実際の予約番号とセッション番号。

エージェントへの指示：配った数は参考の値で、来店までの道のりの分母にしない。履歴から言えることも観測までにとどめ、原因は仮説として書く。

### 調べ方

1. **検算**：書き出しから来店までの道のりと内訳をコードで数え直し、アプリの数字と比べる。合わなければ、分析より先に「食い違い」として報告する。一致しても「台帳が正しい」とは言わない（同じ入力に対する2つの集計が一致した、まで）
2. **見立てを置く**：段ごとの離脱数と離脱率、媒体ごとの来店率から、最初の見立てを1つ書く
3. **集計を重ねる**：見立てを確かめる軸（予約から確定日時までの日数・曜日・メニューなど）を選んで集計し直す。結果を見て、見立てを直すか次の軸を選ぶ
4. **報告**：「観測した事実」「原因の仮説」「追加で確かめること」を分けて書く。次の一手は **店全体で1つ**

### 実行の記録

- エージェントが回した集計（コード・結果・実行の番号）は、**アプリの側で** エージェントの実行の出来事から拾って `analysis_runs.tool_log` に残す。Claude が報告に書いた文章だけを記録として扱わない
- エージェントは集計1回ごとにスクリプトを `/workspace/steps/step_NN.py` に書いて実行する。報告の観測は根拠の `step_NN` を持ち、アプリの記録の実行したコマンドと名前で突き合わせられる
- 画面では「何を集計し → 何が出て → どう見立てを変えたか」を短く並べ、アプリの側の記録（実行した道具の入力と出力）も開いて見られるようにする

### 報告の形（JSON）

形は `agent/report_schema.json` で決める。主な項目：

| 項目 | 中身 |
|---|---|
| `reconciliation` | 検算の結果（一致したか・数え直した件数・食い違い） |
| `first_view` / `revised_view` | 最初の見立てと、集計を重ねた後の見立て |
| `view_changed` | 見立ての中身が変わったか（画面の案内役のひと言はこれで決める。文字の比較はしない） |
| `steps` | 集計1回ごとの記録（`step_01` など・何を確かめたか・何が出たか・どう決めたか） |
| `observations` | 観測した事実。分子・分母・集計の条件・根拠の `step` を必ず持つ |
| `hypotheses` / `to_check` | 原因の仮説（確かめ方つき）と、台帳だけでは確かめられないこと |
| `next_action` | 店全体で1つ。手間・見る数字・比べる相手と期間・仮置きの目標 |
| `previous_review` | 前回の分析の「次の一手」のその後（前回の時点の数字 → 今の数字・変化の内訳）。前回の一手と集計は `previous.json` で渡す。分析が回を重ねて1周する（DX 担当がいなくても回る）ための項目 |

- `first_view` → `revised_view`：最初の見立てと、追加の集計の後の見立て（変わらなければ同じでよい）
- `next_action` の目標値は試すための仮置き。超えても、それだけで「施策が効いた」とは言わない（比べる相手と期間を書く）

### 仕上がりの基準（outcomes に渡す）

- すべての観測に、分子・分母・集計の条件・根拠の `step_NN` が付いている（基準の全文は `agent/rubric.md`）
- 検算がアプリの数字と一致している（または、食い違いを先に報告している）
- 観測・仮説・追加で確かめることが分かれている
- 許可していない列の値が出ていない

### 確かめ方

- 仕込みのある台帳と無い台帳の2つで回し、見立てと調べ方が変わるかを見る。無い台帳で「差が縮む」と言い出さないこと
- 見本の天候（§6）を足した後は、天候を渡しても「天候の効果」を観測として言わないこと（効果の無いように作ってあるため）。言うなら件数が足りないことを添えた仮説まで

### 11/3 までに確かめたこと

- `claude-opus-5-5` と Managed Agents は、このアカウントで使えた（11/2：仕込みあり $0.82・約5分、仕込みなし $1.17・約7分）
- コードを実行する道具：エージェントが集計1回ごとに `step_NN.py` を書いて実行し、道具の呼び出しと結果はアプリの側で出来事の流れから拾って記録する
- 1回の分析は Opus で約5〜7分・$0.82〜$1.26（BUILD_LOG の実測）。使う量の上限は `VL_BUDGET_CENTS`（既定 300 セント）で、超えたら止める
- 失敗した時：報告の形が合わなければ違う所を出して「失敗」にする。サーバーを立ち上げ直しても、実行中の分析はセッションが終わるのを待って報告を受け取る
- Messages API を1回呼ぶ予備の形（`VL_ANALYSIS_MODE=messages`）は、同じ入力・同じ報告の形で残してある。Managed Agents が動いたので、ふだんは使っていない。使う時も追加の集計はできないので、「同じ力」とは言わない

エージェントの定義（指示文・道具・基準）はファイルにして `agent/` に置き、変更を git で追えるようにする。

## 12. 言わないこと

- 「この施策が来店を生んだ」とは言わない。言えるのは「この施策経由の予約が来店した」まで
- 予算の配分（チラシを減らす・LINE に寄せる）を決められるとは言わない。費用・粗利・電話だけの予約を持っていない
- チラシ・LINE を「新しい集客」とは呼ばない（新しいお客様か分からない）。「店の外からの予約経路」と呼ぶ
- 来店の記録が無いことを「来なかった」とは言わない。「来店未記録」と呼ぶ
- 曜日や日数で差が出ても、それを原因とは言わない
- 検算が一致しても「台帳が正しい」とは言わない
- 「匿名化した」「業務アプリにそのまま移せる」とは言わない（試していない）
- 「店長の判断を変えた」は目標であって実績ではない。見本で仕込みが見つかっても、本物の店で効果が出た証拠とは言わない
